# 技术选型报告：多开空间 + 完整谷歌环境

> 调研时间：2026-09　|　调研对象：GBox、GSpace、VMOS、VirtualApp、BlackBox/NewBlackbox、microG、Island/Shelter、AVF

---

## 一、问题拆解

用户需求可以拆成三个**彼此独立**的技术问题。很多方案失败的原因是把它们混在一起做：

| # | 子问题 | 本质 |
|---|---|---|
| A | **多开**：同一个应用跑 N 份，数据互不干扰 | 进程 / uid / 文件系统视图的隔离 |
| B | **谷歌环境**：让应用以为设备有 GMS | 提供 `com.google.android.gms` 等包的实现 |
| C | **账号登录**：能真的登进 Google 账号 | 让 B 的实现通过应用的签名校验 |

C 是 B 的前置条件，而且是最难的一环——它需要**签名伪造**。

## 二、候选方案全景对比

### 2.1 面向子问题 A（多开）

| 方案 | 原理 | 多开上限 | 免 Root | 性能损耗 | 磁盘占用 | 授权 | 可行性 |
|---|---|---|---|---|---|---|---|
| **工作资料（Island / Shelter）** | 系统 Work Profile | **2**（个人 + 工作） | ✅ | 极低 | 低 | Apache-2.0 | 只能双开，不满足需求 |
| **应用层虚拟化容器**<br>（VirtualApp / BlackBox / 双开助手系） | 在同一进程内 Hook AMS/PMS/native，欺骗系统 | 无限 | ✅ | **接近原生** | 应用本体 + 数据 | VirtualApp 商业授权<br>BlackBox Apache-2.0 | ✅ **满足** |
| **完整 Android 虚拟机**<br>（VMOS / 51虚拟机 / GBox 部分实现） | 携带完整系统镜像，容器/半虚拟化运行 | 有限（每个 VM 都很重） | ✅ | 中～高（指令翻译 / 双份 ART） | **1～3 GB** | 闭源 | 占用过大，与需求冲突 |
| **AVF / pKVM（Android 官方虚拟化）** | Hypervisor 级虚拟机 | 理论无限 | — | 低 | 高 | AOSP | 需要系统/HAL 支持，**普通应用无法使用** |

**结论：应用层虚拟化容器是唯一同时满足「无限多开 + 免 Root + 高性能 + 小占用」的路线。**

### 2.2 面向子问题 B + C（谷歌环境 + 账号登录）

| 方案 | 做法 | 需要 Root | 需要改 ROM | 包体 | 许可 | 可行性 |
|---|---|---|---|---|---|---|
| **原版 GMS 全家桶** | 直接塞进容器 | ✅ 通常 | ✅ | 300MB+ | **不可再分发** | ❌ 法律风险 |
| **microG** | 开源重实现 Play Services | ✅ / 或改 ROM | 提供签名伪造补丁 | ~100MB | **Apache-2.0** | ✅ 可分发可改造 |
| **GSpace / GBox 内置 GMS** | 闭源方案内置 | ❌ | ❌ | 大 | 闭源 | ❌ 不可复用、不可审计 |
| **出境易等** | 应用层转译 | ❌ | ❌ | 中 | 闭源 | ❌ |

**结论：microG 是唯一许可清晰、可分发、可二次开发的谷歌环境实现。**

### 2.3 关键难点：microG 怎么过签名校验

microG 用的是自己的密钥，而应用在连接前会校验 `com.google.android.gms` 的签名是否为
Google 官方签名。不过校验的表现形式是「Google Play 服务不可用」或登录报 `12500`。

业界现有的三条破解路径：

| 路径 | 做法 | 门槛 |
|---|---|---|
| 改 ROM | 给 framework 打 signature spoofing 补丁，定义 `FAKE_PACKAGE_SIGNATURE` 权限 | 刷机，极高 |
| Root + Magisk | microG Installer Revived 之类的模块 | Root，高，且有风控风险 |
| **容器内 Hook PMS** | 在虚拟化容器的 PackageManagerService Hook 点额外挂一条签名替换规则 | **零** |

**第三条路是本项目的核心创新点。** 它之所以成立，是因为虚拟化容器为了实现「未安装的 APK
看起来已安装」，**本来就必须 Hook PackageManagerService**。我们只是复用同一个 Hook 点。

```
应用的调用链：
  app.getPackageInfo("com.google.android.gms", GET_SIGNATURES)
      ↓  （进入容器 Hook 层）
  [容器 PMS Hook]
      ├─ 原本的职责：把未安装的包伪装成已安装        ← 容器本来就要做的事
      └─ 新增的职责：把 Signature[] 换成 Google 官方签名  ← 我们加的一条规则
      ↓
  app 拿到 Google 签名 → 校验通过 → 连接 microG
```

### 3.1 为什么虚拟化引擎用「反射适配」而不是直接编译依赖

`BlackBoxEngine` 不把 Bcore 的类编译进依赖图，而是通过反射桥接。原因：

1. Bcore 是重 native 的模块，编译期强耦合会让整个工程的构建门槛变高；
2. 便于在 CI / 无 NDK 环境下降级到 `SandboxEngine`，UI 与业务流程仍可验证；
3. 便于日后替换为商业授权版 VirtualApp 或自研引擎而**不动上层任何代码**。

接入方式：把 Bcore 编出的 AAR 放到 `engine/libs/bcore.aar`，`createOrNull()` 会自动探测。

### 3.2 为什么 microG 默认不打包进 APK

| 方案 | 宿主包体 | 首次使用 |
|---|---|---|
| 内置 microG | ~112 MB | 立即可用 |
| **按需下载（默认）** | **~12 MB** | 装配时下载约 100MB，跨空间共享缓存 |
| 离线预置（可选） | ~112 MB | 立即可用 |

默认走按需下载，理由：大多数用户不会给每个空间都开谷歌环境；而且 GBox / GSpace 也是首启再拉取。
需要离线分发的场景可以跑 `tools/fetch-microg.sh` 把 APK 预置进 assets。

### 3.3 语言选择理由

| 层 | 语言 | 理由 |
|---|---|---|
| UI / 业务 | **Kotlin** | Compose 唯一选择；协程天然适合「下载 + 装配 + 进度回报」这类异步编排 |
| 虚拟化容器核心 | **Java** | Bcore / VirtualApp 血统是 Java，Hook 需要大量反射与动态代理，Kotlin 在这类场景反而更啰嗦 |
| Native 层 | **C++ (NDK)** | PLT Hook 必须操作 ELF 与 GOT，无法用托管语言完成 |
| 跨进程 | **AIDL** | 容器需要 VAServer 独立进程承载虚拟应用的安装与生命周期 |

## 四、性能与占用预算

| 项目 | 预算 | 说明 |
|---|---|---|
| 宿主 APK | < 10 MB | 不含 microG |
| 运行时内存（无空间运行） | ~40 MB | 仅宿主进程 |
| 每个空间额外内存 | 0（空闲）/ 应用自身内存 | 虚拟化容器不为空间常驻进程 |
| 每个空间磁盘 | 应用 APK + 数据 | 不复制系统镜像 |
| microG 磁盘 | ~107 MB（全局一份，跨空间共享） | 不是每个空间一份 |
| 启动一个虚拟应用 | 与原生启动同量级 | 无指令翻译 |

对比：完整 Android 虚拟机方案（VMOS 类）单个实例就需要 1～3 GB 磁盘 + 1～2 GB 常驻内存。
**应用层虚拟化在「高性能、小占用」这两个指标上有一个数量级的优势。**

## 五、风险与已知限制

| 风险 | 影响 | 缓解 |
|---|---|---|
| Bcore 对 Android 15+ 的适配 | 新系统上部分应用启动失败 | 关注 NewBlackbox 上游；必要时自研 native hook |
| Android 6+ packed relocations（APS2） | 自研 PLT Hook 可能扫不到 `.rela.plt` | 引入 Dobby / xDL 做 inline hook（CMake 已预留开关） |
| microG 的 Google 登录仍属实验性 | 部分应用登录失败 | 自检面板如实告知；可换用真 GMS 私有构建 |
| 风控 | 部分应用会检测虚拟环境 | 设备指纹伪装 + 后续可加 Hook 隐藏检测点 |
| 应用层虚拟化的固有边界 | 依赖内核态特性的应用（部分游戏反外挂）无法运行 | 无解，属技术路线边界 |
