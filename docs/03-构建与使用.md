# 构建与使用

## 一、环境要求

### 主工程

| 组件 | 版本 | 说明 |
|---|---|---|
| JDK | **17** | AGP 8.7 要求 JDK 17+ |
| Android SDK Platform | **android-35** | compileSdk / targetSdk |
| Android Build Tools | **35.0.0** | |

## 二、从零搭建环境（Windows / 命令行）

```bash
# 1) JDK 17（Temurin）
curl -L -o jdk17.zip "https://api.adoptium.net/v3/binary/latest/17/ga/windows/x64/jdk/hotspot/normal/eclipse?project=jdk"
unzip -q jdk17.zip -d C:/Users/<you>/android-dev/jdk

# 2) Android SDK 命令行工具
curl -L -o cmdline-tools.zip "https://dl.google.com/android/repository/commandlinetools-win-15859902_latest.zip"
unzip -q cmdline-tools.zip -d sdk-tmp
mkdir -p C:/Users/<you>/android-dev/sdk/cmdline-tools
mv sdk-tmp/cmdline-tools C:/Users/<you>/android-dev/sdk/cmdline-tools/latest

# 3) 安装 SDK 组件
export JAVA_HOME="C:/Users/<you>/android-dev/jdk/jdk-17.0.20.1+1"
SDK=C:/Users/<you>/android-dev/sdk
yes | "$SDK/cmdline-tools/latest/bin/sdkmanager.bat" --sdk_root="$SDK" --licenses
"$SDK/cmdline-tools/latest/bin/sdkmanager.bat" --sdk_root="$SDK" \
  "platform-tools" "platforms;android-35" "build-tools;35.0.0" "ndk;26.1.10909125"
```

> **注意**：`sdkmanager` 装 `platforms;android-35` 会下载 200MB+，
> 期间**不要**同时跑 Gradle 构建，否则会因平台目录写入竞态而报
> `Failed to install the following SDK components`。

### 两个发行变体

| 变体 | 命令 | 宿主包体 | microG 来源 |
|---|---|---|---|
| **lite**（默认） | `./gradlew :app:assembleLiteDebug` | **12.3MB**（clean 实测） | 首次装配时联网下载 |
| **full** | `./gradlew :app:assembleFullDebug` | ~112MB | 打包进 APK，**离线可用** |

两者业务代码完全一致，只差 `assets/microg/` 里有没有 APK。`full` 变体在构建时
由 `:app:fetchMicroG` 任务自动下载 microG 组件（已存在则跳过）。

> **增量构建会让 APK 虚胖约 4MB，属工具链行为，不是代码问题。**
>
> 实测同一个 commit：
>
> | 构建方式 | APK 大小 |
> |---|---|
> | `:app:assembleLiteDebug`（增量） | 17,639,465 字节（16.8MB） |
> | `:app:clean :app:assembleLiteDebug` | 12,862,856 字节（12.3MB） |
>
> 用 ZIP 结构扫描定位到：多出来的 **4,170,012 字节是一段空洞**，
> 紧跟在 `classes15.dex`（本身只有 34,464 字节）之后。
> 这是 `zipalign` 的对齐填充——它用「0 长度本地文件头 + 65505 字节 extra」
> 把 `.dex` / `.so` 对齐到页边界，增量构建时输入文件的对齐状态与 clean 时不同，
> 于是填充量也不同。
>
> **结论**：量体积、发版打包前先 `clean`。看到增量构建的 16.8MB 不要去找代码原因。

> **体积是怎么压下来的**（这条踩过坑，别再踩回去）：
> `androidx.compose.material:material-icons-extended` 含 4264 个图标 × 5 种主题
> ≈ 21320 个类，会**全部**进 dex——因为本工程 debug/release 都没开 minify。
> 实测它占了 dex 全部类引用符号的 **63.5%**。工程只用 5 个图标
> （`Add` / `Delete` / `Settings` / `PlayArrow` / `AutoMirrored.Filled.ArrowBack`），
> 全部在 `material-icons-core` 的 49 个之内。换成 core 后 APK 从 20.9MB 降到 12.4MB。

```bash
# 其他常用命令
./gradlew :app:assembleLiteRelease      # Release APK
./gradlew :native:assembleDebug         # 只编 native，快速验证 PLT Hook 能过编译
./gradlew :app:installLiteDebug         # 装到已连接设备
```

产物路径：
```
app/build/outputs/apk/lite/debug/app-lite-debug.apk
app/build/outputs/apk/full/debug/app-full-debug.apk
```

## 五、预置 microG（可选，用于离线分发）

默认情况下应用会在首次装配时自行下载 microG。若要离线可用：

```bash
# macOS / Linux / Git Bash
chmod +x tools/fetch-microg.sh
./tools/fetch-microg.sh           # 标准变体
./tools/fetch-microg.sh --hw      # 华为/荣耀变体
./tools/fetch-microg.sh --clean   # 清空
```

```powershell
# Windows PowerShell
powershell -ExecutionPolicy Bypass -File tools\fetch-microg.ps1
powershell -ExecutionPolicy Bypass -File tools\fetch-microg.ps1 -Huawei
powershell -ExecutionPolicy Bypass -File tools\fetch-microg.ps1 -Clean
```

下载到 `gms/src/main/assets/microg/`。这些 APK 已在 `.gitignore` 中排除。
**注意：预置后 APK 体积会从 ~12MB 涨到 ~112MB。**

可选组件 `GsfProxy` 不在 GmsCore 仓库中，需要从各自仓库手动下载后放入同一目录。

## 六、使用流程

1. **启动应用** → 启动页显示引擎名（`bcore` = 真引擎，`sandbox` = 降级）与 native 版本
2. **新建空间** → 填名称、选主题色、选设备指纹档位、勾选「启用谷歌环境」
3. **进入空间** → 点「装配谷歌环境」→ 等待下载与安装（进度条实时显示）
4. **点「自检」** → 确认各组全部 PASS
5. **登录 Google 账号** → 空间详情页点「登录 Google 账号」
6. **装个应用商店** → 「应用商店」区块点「装入应用商店」（Aurora Store）
7. **在空间里下载应用** → 打开商店，登录 Google 账号，搜索并下载；
   下载的 APK 会**自动装进当前空间**
8. **也可从宿主导入** → 「从已安装应用导入」，或「从文件装入 APK」

> **在模拟器上测试**：x86_64 模拟器（MuMu 等）带 ARM 翻译层，可以正常跑。
> 但有两个坑必须避开——漏掉 `black-reflection.jar` 或让 APK 里出现
> `lib/x86_64/`，都会让引擎**静默降级**而 UI 看起来完全正常。
> 完整说明、adb 操作注意事项与一键脚本见
> **[07-本地测试与模拟器适配.md](07-本地测试与模拟器适配.md)**。

### 应用商店与「容器内安装路由」

空间里没有商店时，用「装入应用商店」一键装 **Aurora Store**（GPLv3 开源，
Google Play 的第三方客户端，支持登录 Google 账号，与 microG 官方兼容）。

关键点在于：**商店下载的应用会装进当前空间，而不是宿主机**。

这需要容器接管安装 Intent——Bcore 默认不接管时会把它转发给**系统安装器**，
结果是应用装到了外面。我们在 `ClientConfiguration.requestInstallPackage` 里
返回 `true` 接管，再用 `userId` 定位空间后异步装入。

「空间内安装记录」会显示每次安装的结果。这条路径对**任何**商店都生效，
不限于 Aurora Store——F-Droid 之类用「从文件装入 APK」装进去同样能用。

为什么不内置 Play 商店：原版 GMS / Play 商店不可再分发，且需要绕过 Google 的
设备认证（Play Integrity）。完整对比见 **[05-GBox机制解析与商店方案.md](05-GBox机制解析与商店方案.md)**。

### 「从已安装应用导入」适合什么场景

容器直接读系统的安装路径（宿主就是容器自己），因此：

- 不需要存储权限，也不产生临时文件；
- 宿主上已经装好的应用可以直接进来，不用先想办法导出 APK；
- 系统应用、预装应用同样适用（默认不显示，打开面板里的「包含系统应用」开关）。

**但要注意一个限制**：容器侧 `installPackageAsUser(String, int)` 只透传
`sourceDir`，`splitSourceDirs` 会被丢弃。所以 **AAB 拆分包目前只装入基础 APK**，
运行时多半缺资源。导入列表里带「拆分包 N 项」标记的就是这类应用——
芯片用的是警示色，文案写明「仅装基础包」。

这条对「克隆谷歌系列应用」影响很大：Google 自家应用（Maps / Chrome / YouTube）
全是 AAB 拆分包。修复方向见 **[09-应用安装与宿主克隆.md](09-应用安装与宿主克隆.md)** 第 3 节。

### 空间保活与内存回收（设置页）

**为什么需要它**：虚拟应用并不是"另一个 App 的进程"，而是**从宿主进程 fork 出来的**。
宿主一旦被系统回收，空间里所有正在运行的应用会一起消失——用户切回来看到的是
重新冷启动，登录态甚至要重走一遍。免 Root 前提下，把宿主提到前台服务优先级
（降低 `oom_adj`）是唯一能显著改善这件事的手段。

在**设置 → 空间保活**里开启。开启后：

- 通知栏出现一条常驻通知，实时显示「N 个空间 · M 个应用驻留」；
- 通知权限会在**你按下开关的那一刻**才申请——冷启动就弹窗很容易被随手拒掉，
  而 Android 13 的权限弹窗被拒后系统不再弹第二次；
- 关闭保活会同时清空"最近使用"顺序，避免下次开启时按过期数据误判。

**回收策略**（`MemoryGovernor`，纯函数 + 8 组单元测试）：

| 触发档位 | 含义 | 保留预算 |
|---|---|---|
| `TRIM_MEMORY_UI_HIDDEN` / 手动 | 用户已离开 App，从容瘦身 | 2 个进程 |
| `TRIM_MEMORY_BACKGROUND` | 已被列入后台待回收名单，得赶紧 | 1 个进程 |

预算之内按「最近使用」顺序保留，之外全部回收。**从没被打开过的进程优先被回收。**
用户当前打开的那个空间会被"钉住"，永远不参与回收——否则切回来就是一次冷启动。

> ⚠️ **一个值得记下的坑**：网上常见的写法是监听 `TRIM_MEMORY_RUNNING_LOW` /
> `RUNNING_CRITICAL`。但这两个常量连同 `MODERATE` / `COMPLETE` 在 **API 35 的
> `android.jar` 里已经全部带上 `@Deprecated`**，只有 `UI_HIDDEN` 和 `BACKGROUND`
> 还是有效档位。照抄教科书会得到一个**永远不会触发**的回收器。
> 本工程以 `UI_HIDDEN` 为主触发点，同时保留旧档位映射以兼容老设备。

设置页的「立即按内存压力回收一次」按钮可用来现场验证策略；结果会显示在
「最近回收」一行里。

### 自检不通过怎么办

| 现象 | 原因 | 处理 |
|---|---|---|
| 「容器能力」显示降级沙箱 | AAR 未接入 | 放 `engine/libs/bcore.aar`，见第七节 |
| 「组件安装」缺失 GmsCore | 下载失败 | 换网络重试，或用 `tools/fetch-microg.sh` 预置 |
| 「签名伪造」WARN：证书缺失 | 未投放证书 | 正常。本地测试不需要它，见 [06](06-签名伪造与本地测试.md) |
| 「签名伪造」FAIL：链路不通 | 引擎未注册钩子 | AAR 太旧，重跑 `tools/build-bcore.sh` |
| 「设备指纹」WARN | 未配置 | 在空间设置里选一个指纹档位 |

### 关于签名伪造（详细说明见文档 06）

一句话结论：**本地测试不需要签名伪造**。microG 自检 + 登录 + Aurora Store 下载安装
这条主链路，与「容器向虚拟应用呈现什么 GMS 签名」无关。

只有当你**必须**让容器内的 microG 自检报告「签名匹配」时，才需要它。而比对方式是：

```java
// 对签名证书的**原始 DER 字节**做 SHA-1，再与常量比对
byte[] digest = sha1bytes(sig.toByteArray());
GMS_PACKAGE_SIGNATURE_SHA1.equals(bytesToSumString(digest))
```

常量是 `38918a453d07199354f8b19af05ec6562ced5788`。SHA-1 不可反推，
所以**任何自签的临时证书都骗不过它**——`new Signature(String)` 只是按 ASCII 取字节，
并不能"把 SHA-1 变成证书"。网上流传的"填个 SHA-1 字符串就能伪造"是错的。

本工程提供三态模式（空间详情页可直接切换）：

| 模式 | 用途 | 自检结果 |
|---|---|---|
| `OFF`（默认） | 本地测试 / 日常使用 | SKIP，不计入失败 |
| `TEST` | 用 `tools/gen-test-cert.sh` 生成的自签证书**验证整条链路通不通** | WARN（链路通，但证书非官方） |
| `OFFICIAL` | 投放自己合法持有的 Google 平台证书，真正通过 microG 校验 | PASS |

**官方证书怎么拿**：从你自己设备上的 GMS 包里导出，一条命令：

```bash
adb shell pm path com.google.android.gms      # 拿到 base.apk 路径
adb pull <上面输出的路径> gms.apk
tools/extract-gms-cert.sh gms.apk             # 导出 + 自动核对指纹
```

脚本会解析 APK Signing Block（v1/v2/v3 都支持），输出证书主体、SHA-1/SHA-256，
并**自动核对**是否等于 `38918a453d07199354f8b19af05ec6562ced5788`。
产物落在 `local/signature/google_platform.der`（已在 `.gitignore` 里）。

> ⚠️ **证书不随项目分发**，只能自备——这与"不打包原版 GMS"是同一条合规红线。
> 另外，`keytool -printcert -jarfile` 和 `unzip -p ... META-INF/CERT.RSA`
> 这两条流传很广的配方**对现代 GMS 包已经失效**：那些包普遍没有 v1 签名。
> 原因详见 [06-签名伪造与本地测试.md](06-签名伪造与本地测试.md) 的路线 C。

`TEST` 模式的价值是**把"链路没通"和"证书不对"两个问题分开**：
如果 `TEST` 下自检报「链路通、证书非官方」，说明容器 PMS Hook、策略下发、
跨进程读取全部正确，换成官方证书即可通过。

完整流程、证书查找顺序、常见问题见 **[06-签名伪造与本地测试.md](06-签名伪造与本地测试.md)**。

## 七、接入虚拟化引擎（Bcore）

> **本工程已接入。** 下面说明机制，并给出从零重建的方法。

### 7.1 构建 AAR

Bcore 以源码形式分发，没有官方 Maven 包，需要自己编出 AAR：

```bash
# 需要 JDK 21 + NDK 29（见第一节）
tools/build-bcore.sh

# 自定义路径 / 上游地址
JDK21_HOME=/path/to/jdk21 DOOBLE_DEV=/path/to/dev tools/build-bcore.sh <git-url>
```

脚本会克隆上游、应用 `tools/bcore-patch/` 下的补丁（幂等）、构建
`:Bcore:assembleDebug`、做一次 AAR 瘦身、再把产物拷到 `engine/libs/bcore.aar`。
native 层首次编译约 10 分钟，之后增量很快。

**补丁集**（`tools/bcore-patch/`，按文件名排序依次应用）：

| 补丁 | 内容 |
|---|---|
| `0001-container-signature-spoofer.patch` | 容器级签名伪造的接入点（`PackageManagerCompat` 里 `pi.signatures` 的唯一填充处） |
| `0002-container-package-installer.patch` | 容器自持的 `IPackageInstaller` 代理，让空间内的商店能装应用（见 docs/05 第 3.3 节） |
| `0003-recents-and-store-routing.patch` | 最近任务里显示真实应用名与图标；`market://` / `play.google.com` 链接路由到容器内的商店（见 docs/08） |
| `0004-resolve-activity-ambiguity.patch` | `chooseBestActivity` 在候选同权时不再返回 `null`（原来会让容器内的商店拿到 `null` 后 NPE 打不开）；见 docs/08 第 5.5 节 |
| `0014-session-callback-status.patch` | 容器 PackageInstaller 会话回调（`onSessionCreated`/`onSessionFinished` 主动触发），修复商店「一直显示正在安装中」状态不同步（见 docs/13） |
| `0015-dns-delegate-real-system.patch` | 容器 `getDnsServers` 透传真实系统 DNS，不再硬编码 `8.8.8.8/8.8.4.4`（见 docs/13） |
| `0016-install-result-broadcast-sender.patch` | 容器安装结果回传（`BRActivityThread.sendActivityResult` 投递 `RESULT_OK`）+ 广播 PendingIntent 的宿主包装与 extras 合并，修复 F-Droid 旧安装器/会话安装器「装完不刷新」 |

补丁是**幂等**的：已经应用过的会打印 `[skip ]`，不会重复打、也不会报错。

> **写新补丁时的一条硬规矩**：新补丁的改动**不能落进已有补丁 hunk 的 3 行上下文窗口**。
>
> 补丁是顺序应用的。如果 0003 改了紧挨着 0002 插入点的那几行，0002 的
> `git apply --reverse --check` 就会失败（上下文被改了），脚本会把「已应用」
> 误判成「上游改了代码」而中止。`build-bcore.sh` 里用 `-C1` 做了兜底探测，
> 但根治办法是物理上把改动挪开——见 `BlackBoxCore.getStorePackages()` 的注释。

**AAR 里有什么**（约 2.1MB）：

```
classes.jar                          2711 个类（容器核心）
jni/arm64-v8a/libblackbox.so         ELF 解析 + Dobby inline hook
jni/armeabi-v7a/libblackbox.so
assets/empty.jar                     容器 ClassLoader 的兜底 DEX 加载目标（必需）
AndroidManifest.xml                  全部虚拟组件与进程声明（128KB）
R.txt                                消费方 AGP 据此生成 top.niunaijun.blackbox.R
```

**同目录下还有第二个产物 `black-reflection.jar`**（20KB）：
Bcore 对上游 `:black-reflection` 模块是 `implementation` 依赖，AAR 不传递，
而那个模块没有 Maven 坐标、Gradle 也捞不回来。漏掉它会在 `BlackBoxCore`
初始化时抛 `NoClassDefFoundError`，**表现为引擎静默降级**。
详见 [07-本地测试与模拟器适配.md](07-本地测试与模拟器适配.md) 第二节。

> **AAR 瘦身**：上游 assets 里还有一个 `junit.jar`（87KB），但 `JarConfig` 里它是
> `required = false`，全工程唯一的引用点是上游的开发自测类 `JarManagerTest`。
> `build-bcore.sh` 会在打包时删掉它，运行时只会多一条 "Optional JAR file missing"
> 日志。`empty.jar` 不能删——`NativeCore` / `BActivityThread` 靠它做 DEX 加载兜底。

> **ABI 限制**：上游只为 `arm64-v8a` 和 `armeabi-v7a` 提供 Dobby 预编译库，
> 因此**没有 x86_64 版本**。APK 里也**绝不能出现 `lib/x86_64/`**——
> 否则 `primaryCpuAbi` 会被选成 x86_64，`libblackbox.so` 永远找不到。
> 相关配置与原因见 [07-本地测试与模拟器适配.md](07-本地测试与模拟器适配.md) 第三节。
> x86_64 模拟器（如 MuMu）带 ARM 翻译层，走 `arm64-v8a` 可以正常跑。

### 7.2 编译期绑定，不是反射

`engine/src/bcore/java/` 这个源集只有在 `engine/libs/*.aar` 存在时才会被加入编译
（见 `engine/build.gradle.kts` 里的 `hasBcore` 开关）。它**直接引用 Bcore 的类型**，
方法名 / 签名 / 返回值全部由编译器校验。

为什么不用反射：

1. Bcore 的启动入口 `doAttachBaseContext(Context, ClientConfiguration)` 要求传入一个
   **抽象类**的实例，而 Java 动态代理只能代理接口——反射方案在这一步就断了；
2. 反射调错方法名编译期毫无察觉。本工程就踩过：把 `launchApk` 写成 `launchApp`、
   把 `installPackageAsUser` 当成返回 `String`（实际返回 `InstallResult`），
   运行期静默返回 null，UI 却显示"启动成功"。这类 bug 极难排查。

AAR 缺失时整个源集不参与编译，运行时由 `BcoreEngineFactory` 探测失败后降级到
`SandboxEngine`——工程照常构建，只是不具备真正的多开能力。

### 7.3 Bcore 的 AAR 不带传递依赖

本地 AAR 不含依赖元数据，Bcore 运行时需要的东西必须由宿主显式声明：

| 依赖 | 为什么需要 | 缺了会怎样 |
|---|---|---|
| `com.github.tiann:FreeReflection` | `BlackBoxCore` 调 `Reflection.unseal()` 绕过隐藏 API | 初始化时 `NoClassDefFoundError` |
| `androidx.constraintlayout` | AAR 里 `activity_launcher.xml` 的布局属性 | 资源链接失败，构建中断 |

`FreeReflection` 只发布在 JitPack，所以 `settings.gradle.kts` 里加了
`maven("https://jitpack.io")`（用 `includeGroupByRegex` 限定 group，避免拖慢其他依赖解析）。

另外 AAR 里的 `LauncherTheme` 继承 `Theme.AppCompat.Light.NoActionBar`，而本工程不依赖
AppCompat。由于我们的 `ClientConfiguration` 已关闭 launcher activity
（`isEnableLauncherActivity = false`），这个 Activity 永远不会启动，因此在
`app/src/main/res/values/themes.xml` 里用平台主题覆盖了它——
不必为一个死掉的样式引入 1.5MB 的 AppCompat。

### 7.4 宿主启动是两段式的，不能合并

```
Application.attachBaseContext(base)      ← 同步，不能等
    └─ DoobleContainer.bootstrapHost()   引擎在此完成宿主进程伪装
Application.onCreate()
    └─ DoobleContainer.bootstrap()       异步做重活（native、VAServer、供给层）
```

把 `bootstrapHost` 塞进异步流程是行不通的：`attachBaseContext` 返回时系统已经按
宿主身份完成了进程初始化，之后再改 ClassLoader / 包名就来不及了，虚拟应用会启动即闪退。

Bcore 侧的顺序照抄自官方示例，不可调换：

```
attachBaseContext:  closeCodeInit()
                    onBeforeMainApplicationAttach(app, base)
                    doAttachBaseContext(base, ClientConfiguration)
                    onAfterMainApplicationAttach(app, base)
onCreate:           doCreate()   →  等 areServicesAvailable() 变 true
```

### 7.5 空间 ↔ userId 映射

Bcore 的 `userId = 0` 保留给宿主自身，用户空间从 1 开始分配。
映射关系**持久化**在 `spaces.json` 的 `bcoreUserId` 字段里，不用列表下标推算——
用户删掉中间某个空间后下标会整体前移，两个空间就会指向同一个 userId，
表现是「两个空间的应用和账号互相串味」。这是数据正确性问题，不能靠推算。

## 八、常见构建问题

| 报错 | 原因 | 解决 |
|---|---|---|
| `Failed to install the following SDK components` | 平台包未装完或写入竞态 | 等 `sdkmanager` 跑完再构建；确认 `platforms/android-35/android.jar` 存在 |
| `NDK not configured` | NDK 未安装或版本不匹配 | 装 `ndk;26.1.10909125`，或改 `libs.versions.toml` 里的 `ndk` |
| `resource style/Theme.AppCompat.Light.NoActionBar not found` | Bcore 的 `LauncherTheme` 继承 AppCompat | 已在 `app/src/main/res/values/themes.xml` 覆盖，见 7.3 |
| `attribute layout_constraintTop_toTopOf not found` | 缺 ConstraintLayout | 加 `implementation(libs.androidx.constraintlayout)` |
| `NoClassDefFoundError: me.weishu.reflection.Reflection` | 缺 FreeReflection | 加 JitPack 仓库 + 该依赖 |
| `Unresolved reference: net`（出现在 `.kts` 里） | Gradle Kotlin DSL 把 `java` 解析成插件扩展而非包名 | 脚本顶部加 `import java.net.URI` |
| `libdooble_native.so 加载失败` | 设备 ABI 不在 `abiFilters` 中 | 在 `native/build.gradle.kts` 里补 ABI |
| `JAVA_HOME is not set` | Gradle 找不到 JDK | 构建前 `export JAVA_HOME=...` |
| `Unable to strip ... libblackbox.so` | 本地 NDK 版本与 Bcore 用的不一致 | 只是警告，不影响运行 |
| `ModifyBackup failed ... backup.modify_backup` | 沙箱备份服务被大量 IO 压住（如 NDK 解压） | 等构建结束；或改用 shell 直接写文件 |

## 九、拿到「原版组件」与「签名证书」

这两件事经常被问，因为它们都**不能由本工程提供**（合规红线），但都有明确的
自助路径。这一节把路径写全。

### 9.1 签名证书

签名伪造要真正让 microG 认账，需要 **Google 官方证书**。证书有两种：

| 类型 | 从哪来 | 有什么用 | 骗得过 microG 吗 |
|---|---|---|---|
| 自签测试证书 | `tools/gen-test-cert.sh` 本地生成 | 只验证"伪造链路通不通" | ❌ **不能** |
| Google 官方证书 | 从任意原版 GMS APK 里提取 | OFFICIAL 模式真正生效 | ✅ |

**为什么自签证书骗不过 microG**：microG 比对的是证书**原始 DER 字节的 SHA-1**，
而 SHA-1 不可反推。自签证书的 DER 和官方证书的 DER 完全是两份数据，
指纹对不上，microG 直接判为"签名不符"。所以自签证书的唯一用途是验证
「容器 PMS hook → 返回伪造签名」这条链路本身是通的。

**提取官方证书**：

```bash
# 参数是任意一个原版 GMS 的 APK（com.google.android.gms）
tools/extract-gms-cert.sh /path/to/gms.apk
# 产出 google_platform.der
```

脚本内部走 `tools/extract-apk-cert.py` —— 纯标准库解析 APK Signing Block，
v2 / v3 / v3.1 优先，都没有才回退 v1 的 openssl pkcs7。

> ⚠️ **老配方已经失效**：`keytool -printcert -jarfile` 与
> `unzip -p apk META-INF/CERT.RSA` 对现代 GMS 包不管用（那些包普遍没有 v1 签名）。
> `apksigner verify --print-certs` 只有指纹、**拿不到证书字节**，
> 而容器要的正是字节本身（`new Signature(byte[])`）。

**投放位置**（按优先级）：

```
<filesDir>/dooble/signature/google_platform.der
<getExternalFilesDir(null)>/dooble/signature/google_platform.der
assets/signature/google_platform.der
```

**原版 GMS APK 从哪来**（见 9.2 的通用方法）。

### 9.2 原版谷歌三件套 / Play 商店

本工程**不打包也不下载**它们（专有软件，不可再分发）。三条合法路径：

#### 路径 A：从自己的设备提取（最可靠）

```bash
adb shell pm path com.google.android.gms     # 原版 GMS Core
adb shell pm path com.android.vending        # Play 商店
adb shell pm path com.google.android.gsf     # GSF
# 拿到 /data/app/~~xxx/<pkg>-yyy/base.apk 之后
adb pull /data/app/~~xxx/com.android.vending-yyy/base.apk playstore.apk
```

`/data/app/**` 是全局可读的，**不需要 root**。

> **Windows 上不要用 `adb shell cat` 导出**：会经过 PTY 把换行转成 CRLF，
> 出来的 zip 是坏的。要用 `adb exec-out ... > file`，或者直接 `adb pull`。

#### 路径 B：模拟器自带的谷歌安装器（最省事）

MuMu 自带 `com.nemu.googleinstaller`（MuMu 12 上版本号 12）：

```bash
adb shell am start -n com.nemu.googleinstaller/.MainActivity
```

跑完之后宿主上就有**原版** GMS + Play 商店。然后在空间详情页用
**「从宿主克隆」**把它们装进空间 —— 这条路走的是 Bcore 的 system 语义
（直接引用宿主 `ApplicationInfo`、不复制 APK、不抽 native 库），
容器内它们会呈现为**系统应用**，这正是原版组件能跑起来的前提。

> 其它模拟器/真机同理：只要宿主上有，就能克隆。

#### 路径 C：第三方镜像站

| 站点 | 本环境可达性 | 备注 |
|---|---|---|
| APKMirror | ❌ 连接失败 | Cloudflare |
| APKPure | ❌ 连接失败 | Cloudflare |
| APKMonk | ❌ 连接失败 | — |

（实测时间 2026-09-29。这些站点从大陆网络基本打不开。）

#### 装进空间之后能不能用？

| 组件 | 能装上吗 | 能用吗 |
|---|---|---|
| microG GmsCore / FakeStore | ✅ 官方直链一键装 | ✅ 本工程主链路 |
| microG GSF Proxy | ✅ 官方直链（21.4 KB） | 只服务 2016 年前的老 C2DM/GCM 库 |
| **原版** GMS / Play 商店 | ✅ 从宿主克隆 | ⚠️ **大概率不可用**，见下 |

原版 Play 商店即使装上、能打开，**登录与下载大概率停在「设备未认证」**：

- Play 商店的下载能力依赖 Google 服务端的 **Play Integrity** 判定，需要硬件凭据；
- 社区实测方案（microG + 官方签名 Play Store 达到 `MEETS_DEVICE_INTEGRITY`）
  要求 root + Zygisk 栈 + 特权工厂槽位 + Play Integrity attestation 组件，
  **免 root 容器做不到**；
- 而且 `MEETS_DEVICE_INTEGRITY` 是**服务端判定**，Google 改规则就失效。

**所以本工程主推 Aurora Store**：走同一套 Play 接口、可以登录谷歌账号、
官方明确兼容 microG，且**不做设备认证**，因此实际可用。

### 9.3 华为 / 荣耀设备

| 事实 | 说明 |
|---|---|
| HMS 与 GMS 是两套**并行**框架 | 装 HMS **不会**让谷歌服务变好；谷歌侧由 microG 提供 |
| HMS 组件设备**自带** | `com.huawei.hwid`（HMS Core）、`com.huawei.appmarket`、`com.huawei.android.pushagent` |
| HMS 在本工程里的作用 | 只影响**华为自家应用**能否在空间里跑 —— 它们要调 HMS。空间详情页的「厂商服务」面板支持从宿主克隆 |
| **纯血鸿蒙装不上本应用** | HarmonyOS NEXT（鸿蒙 5.0+）不再兼容 APK，只有 .hap 能跑。能用的只有 HarmonyOS 4.x 及更早 |
| 后台限制更狠 | EMUI / HarmonyOS 的「应用启动管理」默认冻结后台，需把 Dooble 改成「手动管理」并允许自启动 / 关联启动 / 后台活动 |

> GBox 在华为上"必须用"的原因不是 HMS，而是 **2019-05-16 之后发布的华为机型
> 无法取得 GMS 合法授权**，预装三件套跑不起来。跟 HMS 没有因果关系。
