# 08 · 系统集成、最近任务与商店路由

本文覆盖四件"容器跑通之后才会暴露出来"的事：**电源优化白名单**、**桌面快捷方式**、
**最近任务里的应用身份**、**单个应用的结束运行**，以及**容器内的商店路由**。

它们的共同点是：都不是容器内核的一部分，但任何一件没做对，用户都会把它当成
"容器的 bug"。

---

## 1. 电源优化白名单（为什么它不是可选项）

### 问题

虚拟应用是从**宿主进程 fork** 出来的。系统在做 Doze / App Standby 的进程回收时，
判定依据是**宿主包的 uid**——只要宿主被判为「可优化」，整个进程组
（宿主 + 全部空间内的应用）会在熄屏一段时间后被一起冻结或杀掉。

用户看到的现象是「空间里的应用过一会儿就没了」，然后会归因到容器。

### 做法

`app/system/PowerOptimization.kt`：

| 路由 | 意图 | 什么时候走 |
|---|---|---|
| `DIRECT_DIALOG` | `ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` + `package:` uri | 系统支持时（一次点击即可） |
| `SETTINGS_LIST` | `ACTION_IGNORE_BATTERY_OPTIMIZATION_SETTINGS` | 部分 ROM 摘掉了上面那个 action |
| `UNSUPPORTED` | — | 系统低于 6.0，或两条路都不通 |

**必须先在 `resolveActivity` 里预检**：不少国产 ROM 把这个 action 从 Settings 里
删掉了，直接 `startActivity` 会抛 `ActivityNotFoundException`——用户看到的是
"点了没反应 + 一个崩溃日志"。

### 真踩到的坑：Application context 必须带 `FLAG_ACTIVITY_NEW_TASK`

这一条在模拟器上表现为「点了完全没反应」，日志里也什么都没有，非常难查。

`SpaceViewModel` 是通过 `getApplication<Application>()` 拿 context 的。
**从非 Activity 的 Context 启动 Activity，不带 `FLAG_ACTIVITY_NEW_TASK`
会抛 `AndroidRuntimeException`**：

```
android.util.AndroidRuntimeException: Calling startActivity() from outside of an
Activity context requires the FLAG_ACTIVITY_NEW_TASK flag.
```

而这个异常被 `runCatching` 吞掉了，两条路由都被判成失败 → 返回 `Route.UNSUPPORTED`
→ UI 什么都不做。排查时的正确顺序是：

```bash
# 1. 先确认系统侧真的有这个页面（有输出说明 action 没问题）
adb shell am start -a android.settings.REQUEST_IGNORE_BATTERY_OPTIMIZATIONS \
  -d package:com.dooble.space.debug
# → Starting: Intent { ... cmp=com.android.settings/.fuelgauge.RequestIgnoreBatteryOptimizations }

# 2. 系统侧没问题 → 问题一定在自己的代码里 → 给每个失败分支加日志
```

所以现在 `directIntent()` / `settingsIntent()` 都显式加了 `FLAG_ACTIVITY_NEW_TASK`，
并且 `request()` 的**每个失败分支都 `Log.w`**。用 `runCatching` 包住 `startActivity`
本身没问题，但吞掉异常后不留日志，等于把唯一线索抹掉。

清单里需要声明 `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`。它**不授予任何能力**，
只是让上面那个 intent 不抛 `SecurityException`；最终仍要用户在系统弹窗上点允许。
Google Play 对这条权限有政策限制，本工程不通过商店分发。

### 三条提示语不能合并成一条

`SpaceViewModel.requestIgnoreBatteryOptimizations()` 按实际走的路给不同提示：

- 走了确认框 → "请在系统弹窗上点「允许」"
- 只打开了列表页 → "请在里面把「Dooble Double」设为不优化"
- 都不通 → "请到系统设置里手动查找"

**不能笼统地说"已加入白名单"**。用户在列表页里还得自己找本应用，
说成"已加入"会让他以为已经生效了。

### 白名单管不了国产 ROM

AOSP 的 Doze 白名单**不读**小米的神隐模式、华为的应用启动管理、OPPO 的耗电保护。
那是 ROM 自己的一套后台冻结策略，与 AOSP 并行。所以设置页里另给一个
「打开系统自启动管理」入口，内置一张社区长期验证过的组件名表
（MIUI / EMUI / ColorOS / OriginOS / One UI / Flyme）。

表是**尽力而为**的：组件名随 ROM 版本变动是常态，找不到就如实说
"当前 ROM 没有已知的自启管理入口"，而不是假装打开了一个页面。

## 2. 桌面快捷方式

### 为什么是 `requestPinShortcut` 而不是 `setDynamicShortcuts`

两者是完全不同的东西：

| API | 效果 | 代价 |
|---|---|---|
| `setDynamicShortcuts` | 只出现在**长按图标弹出的菜单**里，桌面上什么都不会多 | 无 |
| `requestPinShortcut` | 向启动器请求在**桌面上**钉一个图标 | 必须弹一次系统确认框 |

用户说的"创建桌面快捷方式"是后者。系统强制要求一次确认，应用绕不过去。

**刻意不做"全选 + 一键发送"**：多个钉请求同时到达启动器时，后面的会被静默丢弃，
用户会以为功能坏了。所以 `ShortcutSheet` 一次只钉一个——用户点几下就是钉几个，
行为与操作一一对应。

### 图标来源

复用宿主侧的 `AppIconLoader`：它读的是容器虚拟目录里那份 APK，与空间内实际
运行的是同一个文件，所以桌面上看到的图标和容器里完全一致。

拿不到图标时退回宿主自己的启动图标（`R.mipmap.ic_launcher`）而不是 null——
`IconCompat` 不接受 null。这里刻意不用 `applicationInfo.icon`：只声明了自适应图标
（`mipmap-anydpi-v26`）的应用上它可能是 0，而 0 会让 `IconCompat` 在真正取图时
抛 `NotFoundException`。

### 快捷方式 id 必须稳定

`id = "dooble.app." + hash(spaceId + packageName)`。

同一个 (空间, 应用) 反复钉应当**覆盖**旧条目，而不是在启动器里堆出一串重复项。
用哈希而不是拼原文，是因为 id 有长度上限，而 UUID + 包名很容易超。

### 跳板 Activity

`ShortcutLaunchActivity` 是快捷方式的落地点，主题是 `Theme.Dooble.Trampoline`
（全透明 + `windowDisablePreview` + 不进最近任务 + `noHistory`）。

不直接指向 `MainActivity` 的原因：从桌面冷启动时宿主进程是全新的，
`DoobleContainer.bootstrap()` 还在跑。复用 `MainActivity` 会让用户先看到
完整的空间列表界面闪一下，甚至可能手动点走。

跳板做三件事：等引擎进入 `Ready`（最长 20 秒）→ `engine.launch()` → `finish()`。
失败必须弹 Toast 让用户看见——此时屏幕上没有任何宿主界面，静默 `finish()`
会让用户以为快捷方式坏了却又说不清哪里坏了。

空间快捷方式（不带包名）走 `MainActivity` + `EXTRA_SPACE_ID`，由
`onNewIntent` 投递到 `pendingSpaceId` 这个 StateFlow，等 `spaces` 加载完再跳转
（否则会渲染出一个标题为"空间"的空页面）。

### 跳板 intent 也必须带 `FLAG_ACTIVITY_NEW_TASK`

`pinApp()` 里那个 target intent 一开始漏了这个 flag（`pinSpace()` 有）。
少了它，快捷方式启动时会被塞进**调用方所在的任务栈**——如果用户在宿主界面里
点，就会并进宿主任务，返回键行为错乱（返回一次直接退出到桌面，
而不是回到宿主列表）。两个 `pin*` 现在都显式加了。

### 实测链路（MuMu + Lawnchair）

端到端跑通后的完整证据链：

```
点面板「钉」
  → Lawnchair 弹 CONFIRM_PIN_SHORTCUT（显示的是 Aurora Store 真实图标与名称）
  → 点「添加到主屏幕」
  → 启动器数据库落盘：
      _id=13 | Aurora Store | itemType=6 (DEEP_SHORTCUT)
      | shortcut_id=dooble.app.795e934d | 占位组件 MainActivity
  → 桌面出现带 Aurora 图标的快捷方式
  → 点击后：
      START u0 {act=VIEW flg=0x10000000
                cmp=com.dooble.space.debug/com.dooble.space.system.ShortcutLaunchActivity}
  → ShortcutLaunchActivity（独立任务，affinity = com.dooble.space.shortcut）
  → startActivityLocked : com.aurora.store.ComposeActivity
  → 任务标签「Aurora Store」+ 真实图标
```

两个值得记住的点：

1. **启动器不存你的 Intent，只存 shortcut id**。它把深链记成 `itemType=6`
   （`DEEP_SHORTCUT`）+ `shortcut_id` + 一个 `MainActivity` 占位组件，
   真正启动时走 `LauncherApps.startShortcut`。所以调试时直接去
   `/data/data/<launcher>/databases/*.db` 里看 `shortcut_id` 最直观。
2. **`ShortcutLaunchActivity` 必须有独立 affinity**。共用宿主 affinity 的话，
   它会并进宿主任务，跳板 `finish()` 后整个任务一起消失，用户看到闪一下就没。

### 关于撤销

钉到桌面上的图标**归启动器所有**，应用无权删除（系统有意如此，防止应用偷改
用户桌面）。用户只能在桌面上长按移除。UI 必须提前讲清楚，
否则用户会来找"取消"按钮，然后发现根本没有。

## 3. 最近任务里的应用身份（这一节是最深的坑）

### 现象

空间里所有应用在最近任务里长得**一模一样，全是宿主自己的名字和图标**。

### 根因

虚拟 Activity 在系统眼里是宿主的 stub Activity（`top.niunaijun.blackbox.stub.*`），
它的 `ActivityInfo` 属于**宿主包**。系统构造最近任务卡片时，若拿不到显式的
`TaskDescription`，就会用那个 stub 的 label 与 icon。

**唯一能让系统改口的办法，就是主动 `Activity.setTaskDescription()`。**

Bcore 上游已经有这条链路（`ActivityCompat.fix` → `setTaskDescription` →
三处 `setTaskDescription` 代理钩子 → `TaskDescriptionCompat.fix`），
但实现里埋了三个问题：

| # | 问题 | 表现 |
|---|---|---|
| 1 | `getTaskDescriptionLabel` 返回 `String.format("[B%d]%s", userId, label)` | 最近任务里显示成 `[B1]microG 服务` |
| 2 | 重建 `TaskDescription` 时给 icon 传 `null` | 卡片上没有应用图标 |
| 3 | `getApplicationLabel()` 走 `pm.getApplicationLabel()` | 查不到就静默退化成**包名** |

### 实测证据

```
# 修复前
taskDescription: label="[B1]microG 服务" icon=null
                iconResource=/0 iconFilename=/data/system_ce/0/recent_images/28_activity_icon_*.png
```

`icon=null` 是关键：图标一丢，启动器就回退到"任务所属包"的图标，
也就是**宿主自己的图标**。所以用户看到的是"全是我的双开应用"。

### 图标为什么一定是 null

容器里的 `IPackageManagerProxy` 有一个钩子：

```java
@ProxyMethod("getDrawable")
public static class DisableIconLoading extends MethodHook {
    @Override
    protected Object hook(Object who, Method method, Object[] args) {
        Slog.d(TAG, "Blocking icon loading to prevent resource errors");
        return null;   // ← 永远返回 null
    }
}
```

上游为了规避资源错乱，把 `PackageManager.getDrawable` 直接打回了 null。
于是 `ActivityCompat.getActivityIcon()` 里：

```java
pm.getActivityIcon(componentName)   // 内部 getDrawable -> null -> 退化成默认机器人图标
applicationInfo.loadIcon(pm)        // 同样 getDrawable -> null
```

整条路都拿不到真图标。**注意这是"永远返回 null"而不是"返回错的东西"**——
所以任何依赖 `PackageManager` 取图的代码在容器里都必然失效。

### 修复：绕开 PM，直接读虚拟 APK 的资源表

`TaskDescriptionCompat` 重写后按下面的链条解析（每一步都 try/catch，失败就降级）：

```
1. nonLocalizedLabel                    ← 清单里写死的名字
2. res.getText(info.labelRes)           ← 从虚拟 APK 资源表取
3. pm.getApplicationLabel(info)         ← 资源能加载时也对，但不保证
4. info.packageName                     ← 兜底。不好看，但比宿主名强
```

`Resources` 的来源按可靠性排序：

```
1. BActivityThread.getApplication().getResources()
   ← 虚拟进程里那个 Application 实例，Bcore 按虚拟 APK 建的，一定是这一份
2. pm.getResourcesForApplication(info)
   ← 靠 info.sourceDir 现场加载，宿主进程里也能用
```

图标同理，走 `res.getDrawable(info.icon, null)`，**完全不碰 `PackageManager.getDrawable`**。

`ActivityCompat.fix` 里也换成了同一套（`TaskDescriptionCompat.loadAppIcon()`），
让"应用自己设置"和"容器替它设置"两条路结果一致。

### 尺寸必须封顶

`TaskDescription` 要走 Binder 传给 system_server，事务上限 1MB。
所以图标解码上限钉在 **256px**，并且对 `BitmapDrawable` 快路径返回的原图
再做一次 `createScaledBitmap`——那条路径会直接返回原图，尺寸可能远超上限。

### 顺带确认：任务分离本来就是对的

Bcore 的 `startActivityInNewTaskLocked` 已经加了：

```java
shadow.addFlags(Intent.FLAG_ACTIVITY_MULTIPLE_TASK);
shadow.addFlags(Intent.FLAG_ACTIVITY_NEW_DOCUMENT);
shadow.addFlags(Intent.FLAG_ACTIVITY_NEW_TASK);
```

所以**每个虚拟应用有独立的最近任务卡片**，不需要额外处理。
实测 `dumpsys activity activities` 可以看到每个虚拟应用一个 `Task{}`。

> 但"任务能独立建立"不等于"任务能独立销毁"。
> 结束运行只杀进程，不会收掉卡片——见第 4 节「但引擎不清理任务卡片」。

## 4. 结束单个应用：隔离性本来就是对的

### 链路

```
VirtualEngine.stop(spaceId, packageName)
  └─ BlackBoxCore.stopPackage(packageName, userId)
       └─ BPackageManager.get().stopPackage(pkg, userId)
            └─ BPackageManagerService.stopPackage          // 只有一行
                 └─ BProcessManagerService.killPackageAsUser(pkg, userId)
```

`killPackageAsUser` 的实现：

```java
public void killPackageAsUser(String packageName, int userId) {
    synchronized (mProcessLock) {
        int buid = BUserHandle.getUid(userId, BPackageManagerService.get().getAppId(packageName));
        Map<String, ProcessRecord> process = mProcessMap.get(buid);   // ← 按 (包名, userId) 精确定位
        if (process == null) return;
        for (ProcessRecord value : process.values()) {
            value.kill();
            mPidsSelfLocked.remove(value);
        }
        mProcessMap.remove(buid);
    }
}
```

`mProcessMap` 的 key 是 `buid`（userId + appId），所以：

- 同一个空间里的**其他应用不受影响**；
- 其他空间里的**同名应用不受影响**（userId 不同 → buid 不同）。

**引擎侧本来就是对的**，缺的只是 UI 入口。所以这一项的工作量在宿主侧：
`AppRow` 加了第三个按钮（✕，Tangerine），调 `vm.stopApp(pkg)`。

`stopApp` 里额外做一件事：**把该应用从 LRU 里摘掉**。

```kotlin
KeeperControl.onAppRemoved(getApplication(), id, packageName)
```

进程已经没了，留着它只会让下一次内存回收误判"这是用户最近在用的"，
白保一个死名额。

### 但引擎不清理任务卡片（实测发现的缺口）

`killPackageAsUser` 只做一件事：杀进程。它**不碰**容器的 `ActivityStack`，
也不碰 system_server 里的 `TaskRecord`。而最近任务里的卡片是 system_server
按 stub Activity 建的任务记录 —— **进程死了，任务记录照样躺着**。

实测现象：同时开着 Aurora（任务 #34）与 microG 服务（任务 #35），
点 Aurora 的「结束运行」后：

```
Process com.dooble.space.debug:p2 (pid 14238) has died   ← 进程确实死了
任务 #35 microG 服务                                      ← 完好存活（隔离性 OK）
任务 #34 ProxyActivity$P2                                 ← 卡片还在 ✗
```

用户会认为"结束运行没生效"——甚至再点一次卡片又能把应用拉起来（冷启动）。

**修法在宿主侧**：`app/system/TaskCleaner.kt`。

判定「这张卡片属于哪个虚拟应用」靠 Bcore 写进 stub intent 的两个 extra
（见 `proxy/record/ProxyActivityRecord.saveStub`）：

| extra | 内容 | 用途 |
|---|---|---|
| `_B_|_activity_info_` | 虚拟 `ActivityInfo` | 首选。`packageName` 就是空间内的包名，不受启动方式影响 |
| `_B_|_target_` | 用户原始 intent | 兜底。`component.packageName` 也是虚拟组件 |

```kotlin
val am = context.getSystemService(ACTIVITY_SERVICE) as ActivityManager
for (task in am.appTasks) {
    val base = task.taskInfo?.baseIntent ?: continue
    if (virtualPackageOf(base) != packageName) continue   // 不是这个应用的卡片，放过
    task.finishAndRemoveTask()
}
```

几个关键判断：

- **用 `getAppTasks()` 而不是 `getRecentTasks()`**。虚拟 Activity 的 stub 声明在
  宿主清单里，任务天然挂在宿主名下，`getAppTasks()` 正好能拿到全部空间的卡片；
  而 `getRecentTasks()` 在 Android 5+ 被系统收窄，拿不到别人的任务。
- **认不出来的一律放过**。`virtualPackageOf()` 返回 null 说明这个任务不是容器建的
  （比如宿主自己的 `MainActivity` 任务），绝不能误删。
- **`getAppTasks()` 失败要静默跳过**。部分 ROM 会限制它；卡片残留远好过崩溃。
- **放在宿主侧而不是再打容器补丁**。容器侧要改 `BProcessManagerService` 或给
  `BActivityManager` 加能力 → 重建 AAR（约 7 分钟）+ 重跑一遍补丁幂等性验证。
  而任务记录是 system_server 的公开对象，宿主本来就能操作自己名下的任务。

`uninstall()` 里也调了同一个清理器——应用都卸了，指向它的卡片点开是空的。

#### 修完之后的实测结果

同时拉起 Aurora 与 microG 服务，点 Aurora 的「结束运行」：

| | 点击前 | 点击后 |
|---|---|---|
| 进程 `18189 com.aurora.store` | 存活 | **已消失** |
| 进程 `17406 com.google.android.gms:ui` | 存活 | **仍存活** |
| 任务卡片「Aurora Store」 | 存在 | **已消失** |
| 任务卡片「microG 服务」 | 存在 | **仍存在** |

日志：`DoobleTask: 已收掉 1 张任务卡片：com.aurora.store`

> 注意进程名：虚拟进程在 `/proc` 里的 cmdline 是**被冒充的那个应用自己的包名**
> （容器做进程伪装），不是 `com.dooble.space.debug:pN`。
> 所以验证隔离性时按 `com.aurora.store` / `com.google.android.gms:ui` 去找，
> 见第 7 节的命令。

### 必须和"强制停止宿主"区分开

在系统设置里对 Dooble 做「强行停止」停的是**宿主**，会把所有空间的虚拟进程
一起带走——因为虚拟进程都是从宿主 fork 出来的。这是应用层虚拟化的固有代价，
不是 bug。UI 上单独给一个 ✕ 按钮，就是为了让用户不必去系统设置里做那件危险的事。

### 4.1 补丁：任务卡片的清理必须按**空间**过滤

隔离性在**引擎侧**是对的（`stopPackage(packageName, userId)` 按
`(包名, userId)` 精确匹配），但**宿主侧收任务卡片**那一步一开始漏了 userId：

```kotlin
// 修复前
TaskCleaner.removeTasksOf(context, packageName)
```

后果：同一个应用在空间 A 和空间 B 里都开着时，在空间 A 点「结束运行」
会把空间 B 的卡片也收掉 —— 空间 B 的进程还活着，但用户再也点不开它了。
这正好破坏了第 4 节标题承诺的那条隔离性。

**修法**：stub intent 里其实一直有第三个 extra —— `_B_|_user_id_`
（见 `ProxyActivityRecord.saveStub`，之前只用了 `_B_|_activity_info_`
和 `_B_|_target_`）。把它读出来做归属判定即可。

```kotlin
// 修复后：userId 来自 SpaceRuntime.bcoreUserId
TaskCleaner.removeTasksOf(context, packageName, taskUserIdOf(id))
```

为此做了三处配套改动：

| 改动 | 位置 | 原因 |
|---|---|---|
| `SpaceRuntime.bcoreUserId` | `VirtualEngine.kt` | ViewModel 只有空间 id，拿不到虚拟 userId |
| `BcoreEngine.runtime()` 填充它 | `BcoreEngine.kt` | 数据源在 `SpaceStore.Record` |
| `VirtualTaskResolver` | `app/system/` | 把"读 extra"与"判定归属"拆开，判定才可单测 |

判定规则里有一条**刻意的不对称**，值得记下来：

```kotlin
fun matches(task: VirtualTask, packageName: String, userId: Int?): Boolean {
    if (task.packageName != packageName) return false
    if (userId == null || task.userId == null) return true   // ← 信息不全时按命中处理
    return task.userId == userId
}
```

两种失败的代价不对称：

- **多清一张**：用户少了一张卡片，重开应用即可恢复，几乎无感；
- **漏清一张**：用户点了「结束运行」，卡片还在，再点又能把应用拉起来 ——
  会直接认定这个功能是坏的。

所以只要任一方的 userId 未知，就按"包名相同即命中"处理。

> 同理 `filterUserId(bcoreUserId)` 在 `<= 0`（尚未分配）时返回 **null 而不是 0**。
> 传 0 会变成"只匹配 userId 为 0 的卡片"，而真实卡片是 10000 起的 ——
> 结果是**一张都清不掉**，把"多清"的安全兜底反向变成"全漏"。

**相关文件**：`VirtualTaskResolver.kt`、`TaskCleaner.kt`、`SpaceRuntime`、
`SpaceViewModel.taskUserIdOf`

## 5. 容器内的商店路由

### 问题

空间里的应用（游戏内购页、应用内"更新"按钮、别人的分享链接）经常用
`market://details?id=xxx` 或 `https://play.google.com/store/apps/details?id=xxx`
去唤起商店。

容器里装的是 Aurora Store 这类第三方客户端，它们的 intent-filter 往往只声明了
`scheme=market` 而没有覆盖 `https` + host 的组合。一旦 `resolveActivity` 落空，
Bcore 会把这条 intent **原样交给宿主系统**——结果是宿主机上的浏览器或原版商店
被拉起来。用户看到的是"我在空间里点的，怎么跳到空间外面去了"。

### 做法

在 `ActivityManagerCommonProxy.StartActivity` 里，`resolveActivity` 两次都落空
**之后**、放弃之前，加一次尝试：

```java
if (resolveInfo == null) {
    resolveInfo = resolveStoreIntent(intent);
}
```

`resolveStoreIntent` 拿 `ClientConfiguration.getStorePackages()` 给的名单
逐个 `setPackage()` 重试，命中就把链接交给容器内的商店。

### 为什么只在落空之后才做

空间里如果本来就有能处理这条链接的应用（比如用户装了某个浏览器），
那就该听用户的——强行改道到商店反而是错的。
只有在"容器里谁都不认"的前提下重定向，语义才是清晰的。

### 名单为什么放在 engine

`engine/StorePackages.kt` 是**唯一**的名单来源，`gms/StoreProvisioner.PRIMARY_PACKAGE`
反过来引用它。

这不是"谷歌环境"的知识，而是**容器**的知识：容器在解析链接时需要知道该路由到谁。
供给层决定"装哪个商店"，引擎决定"链接该交给谁"，两者共用同一份名单才能保证
不脱节。`gms/src/test/.../StoreRoutingContractTest.kt` 把"名单形状"钉死
（Aurora 必须第一、FakeStore 必须兜底、不能有空项重复项）。

### 为什么 Aurora 必须排在 FakeStore 之前

microG 的 `com.android.vending` 是 **FakeStore**：它只提供"应用已安装"这个查询的
占位实现，本身没有界面、也没有下载能力。把商店链接交给它，用户看到的是
"点了没反应"。所以必须排在有真实界面的 Aurora Store 之后。

### 只认明确的商店链接

`isStoreIntent` 只接受 `ACTION_VIEW` + 明确命中：

- `scheme == market`，或
- `host` 是 `play.google.com` / `market.android.com`

刻意不做得更"聪明"（比如按 URL 里有没有 `id=` 判断）——猜错会把正常的网页跳转
劫持到商店里，那比不处理更糟。同时显式指定了 `component` 的 intent 一律放行，
因为调用方已经知道要拉谁。

### 为什么容器内的商店一开始打不开（`0004` 补丁）

这是本轮最隐蔽的一个 bug，表现是**点开容器内的谷歌商店直接崩**：

```
java.lang.NullPointerException: Attempt to read from field
'android.content.pm.ActivityInfo android.content.pm.ResolveInfo.activityInfo'
on a null object reference
in method 'void org.microg.vending.ui.MainActivity.onCreate(android.os.Bundle)'
```

根因在 Bcore 的 `BPackageManagerService.chooseBestActivity`。它照着 AOSP 的骨架
写，但**把 AOSP 的歧义分支简化成了 `return null`**。而 AOSP 主线在这个位置
的真实行为是：前两条候选同权 → 查偏好表 → 查不到就构造 ResolverActivity
（"打开方式"选择器）**返回，绝不返回 null**。

触发条件很具体：microG GmsCore 一个包内声明了 **3 条 ACTION_MAIN 过滤器**——

| Activity | category |
|---|---|
| `MainSettingsActivity` | `CATEGORY_DEFAULT` |
| `MainSettingsActivity`（另一条） | `CATEGORY_DEFAULT` |
| `SettingsActivity` | `CATEGORY_LAUNCHER` |

排序后前两条同权 → `chooseBestActivity` 返回 null → FakeStore 拿到 null 再去读
`activityInfo` → NPE。

**修法**：`chooseBestActivity` 退化为「优先取 `isDefault`，其次退回列表首位」，
任何情况下只要有候选就返回一个，绝不返回 null。

```java
if (r0.isDefault) return r0;
for (int i = 1; i < N; i++) {
    ResolveInfo ri = query.get(i);
    if (ri != null && ri.isDefault) return ri;
}
return r0;
```

#### 一个被否掉的方案：补 `MATCH_DEFAULT_ONLY`

我最初的做法是在 `resolveIntent` 里给 flags 补上 `MATCH_DEFAULT_ONLY`，
以为这样能让 3 条候选收敛成 1 条。**这是错的**，而且我一开始是凭记忆下的结论。

下载 AOSP 主线核对（`ResolveIntentHelper.java` / `ComputerEngine.java` /
`PackageManagerServiceUtils.java`）后确认：**resolve 路径根本不补这个 flag**
（它只在 `canForwardTo` 里被手动加过一次）。AOSP 对歧义的处理就是返回
ResolverActivity。所以正确做法是让 `chooseBestActivity` 别返回 null，
而不是去改 flag 让候选变少——后者还会连带影响正常的 intent 解析。

> 教训：涉及系统行为的分支，**先去 AOSP 源码确认，再动手**。
> 凭记忆写出来的"看起来合理"的修法，实测会以完全无关的现象失败。

## 6. 不可逆操作的二次确认

### 为什么必须做

删除空间是这个应用里**唯一彻底不可逆**的操作：空间内的应用、每个应用的数据目录、
存储重定向产生的文件、已登录的 Google 账号，全部一起消失。

而它的两个入口都很容易误触：

| 入口 | 危险在哪 |
|---|---|
| 空间列表卡片上的删除图标 | 只有 **28dp**，而且和"打开空间"同处一张卡片——手指偏几个像素就从"打开"变成"永久删除" |
| 空间详情页的红色整宽按钮 | 滑到底部时很容易顺手点到 |

### 做法：不是问"确定吗"，而是把代价摆出来

只弹一个「确定 / 取消」挡不住真正的误触：用户手指本来在别处，
弹窗出现的瞬间正好落在"确定"上，一次误触就穿透两层。更常见的是**反射性连点**
——弹窗刚出现就按习惯点右边那个按钮。

所以确认框做了三件事：

1. **列出具体代价**（`facts`）：空间名、几个应用、占用多少 MB、谷歌环境是否已装配、
   已登录账号数。「删除空间」这四个字对用户没有信息量，
   把数字摆出来他才会真的停下来读一遍。
2. **强制勾选才放行**：确认按钮默认 `enabled = false`，
   用户必须先勾「我已了解：删除后无法恢复…」。勾选框在按钮**上方**，
   手指必须主动移动，且这一步没有时间压力。
3. **确认按钮不在原按钮的位置**：对话框居中，最终按钮在左半边，
   从卡片删除图标（右上）到这里必须跨过整个屏幕。

组件在 `app/.../ui/components/ConfirmDialog.kt`（`BrutalConfirmDialog`），
空间相关的封装在 `app/.../ui/screens/ConfirmDialogs.kt`。

### 顺带把「卸载应用」也补上了

同一个问题在下一层重复了一次：应用行里的**卸载按钮是 34dp，紧挨着同样 34dp 的
「结束运行」**。一个可恢复（杀进程，再点启动就回来），一个不可恢复（应用数据全没）。
手指偏 34dp 就是"永久"和"临时"的区别。

`UninstallAppDialog` 有两条文案分支：

- **普通应用**：强调数据会被删除，同时明确"**宿主上安装的那一份不受影响**"
  ——空间用的是自己虚拟目录里的副本，不讲清楚用户会以为卸载了空间里的
  就等于卸载了系统的。
- **microG 组件**（`com.google.android.gms` / `com.android.vending` 等）：
  标题改成「卸载谷歌环境组件」，并警告"必须重新执行一次「重新装配」才能恢复"。
  这不是普通卸载，不能和普通应用共用一套措辞。

### 顺带修掉：「磁盘占用」恒为 0

写确认框时发现 `facts` 里「占用磁盘」一直是 `0`——而那个空间里明明装了
8 个应用、几百 MB。查下来是 `SpaceStore.diskUsage` 统计了一个**空目录**：

```kotlin
// 修复前：root 是元数据目录，底下只有 spaces.json
fun diskUsage(spaceId: String): Long = root.resolve(spaceId).walkTopDown()...
```

**这个 bug 的危险之处在于它不报错**：返回值恒为 `0`，而 `0` 是个完全"合法"的
数字——不抛异常、不打警告，UI 上就是安安静静显示 0。看起来只是"还没统计到"，
很容易被当成正常现象放过去。

#### 第一次修错了，值得记一笔

第一反应是"空间数据在 `<root>/virtual/<spaceId>/` 里，改过去就行"。
**这个判断是错的**——`BcoreEngine` 确实会创建 `<filesDir>/dooble/virtual/<spaceId>/`，
所以这个猜测看起来很合理。实测那个目录只有 **1485 字节**。

真实布局要用 `run-as` 去设备上翻：

```
/data/data/<宿主包名>/blackbox/          ← BEnvironment.sVirtualRoot
  data/app/<包名>/                        ← APK 本体（221.9MB）**按包名，无 userId**
  data/user/<userId>/<包名>/              ← 应用数据（1.4MB）按 userId
  data/user_de/<userId>/<包名>/
  cache/ system/ profiles/

<外部私有目录>/blackbox/
  storage/emulated/<userId>/              ← 存储重定向后的 /sdcard
```

即 Bcore 用的是**它自己的**虚拟根，和我们 `filesDir` 下的目录毫无关系。
所以 `<filesDir>/dooble/virtual/` 其实是引擎早期设计的遗留占位。

#### 最终的修法

把路径抽成只依赖 `java.io.File` 的纯函数 `BcoreStorageLayout`
（`engine/.../internal/BcoreStorageLayout.kt`），`SpaceStore.diskUsage`
改成接收调用方传入的目录：

```kotlin
fun diskUsage(vararg dirs: File): Long =
    dirs.sumOf { dir -> dir.walkTopDown().filter { it.isFile }.sumOf { it.length() } }
```

- `SandboxEngine` 传 `virtualRoot.resolve(spaceId)`
- `BcoreEngine` 传 `BcoreStorageLayout.spaceDirs(...)`（需要 `bcoreUserId`）

**为什么交给调用方**：两个引擎的数据位置完全不同，`SpaceStore` 是最没资格
猜这件事的那个类。让最清楚的一方显式传参，"猜错"就从"可能"变成"不可能"。

**一个已知的取舍**：APK 按**包名**存储，同一应用装进两个空间磁盘上只有一份。
`spaceDirs` 按"该空间装了哪些包"归集，所以同名应用出现在多个空间时会被重复
计入，界面顶部合计可能略高于实际。这是有意的——改成只统计
`data/user/<userId>/` 的话数字会小两个数量级（1.4MB vs 223MB），
用户看到"装了 8 个应用只占 1.4MB"只会更困惑。展示用指标"偏大但量级正确"
远好过"精确但恒为 0"。

#### 回归测试

`app/src/test/.../SpaceStoreDiskUsageTest.kt`，**10 个用例**。
不只测"能求和"，更测**路径本身拼得对不对**——那才是当初出错的地方：

- 逐条钉死 `internalRoot` / `appDir` / `userDir` / `userDeDir` / `externalUserDir` 的形状
- `userId == 0` 必须返回空列表（宿主保留值，算进去会凭空多出几百 MB）
- 外部存储不可用时返回 null 而不是抛异常
- 一条端到端用例：按该布局真的落盘文件，再真的统计到它们

### 哪些操作**不**加确认（有意为之）

| 操作 | 为什么不需要 |
|---|---|
| 结束运行 | 杀进程而已，再启动就回来了 |
| 移除 Google 账号 | 重新登录即可恢复；入口在账号区块内，不挨着别的按钮 |
| 清空 microG 缓存 | 只是下载缓存，用户数据不在里面 |

判定标准是一条：**用户数据会消失，且没有撤销入口**。

## 8. 验证方式

```bash
# 最近任务的标题与图标（修复前是 [B1]xxx + icon=null）
adb shell dumpsys activity activities | grep -i "taskDescription: label"

# 每个虚拟应用一个独立任务
adb shell dumpsys activity activities | grep -E "^  \* Task\{"

# 结束单个应用后，同空间其他应用仍在运行
#
# 注意：**不能**用 `ps -A | grep com.dooble.space` —— 容器会做进程伪装，
# 虚拟进程在 /proc 里的 cmdline 是**被冒充的那个应用自己的包名**，例如：
#   17406 com.google.android.gms:ui     ← 容器内的 microG 服务
#   18189 com.aurora.store              ← 容器内的 Aurora Store
# 所以必须按「被冒充的包名」去找：
adb shell 'for p in $(ls /proc | grep -E "^[0-9]+$"); do \
  c=$(tr "\0" " " < /proc/$p/cmdline 2>/dev/null); \
  case "$c" in *aurora*|*google.android.gms*|*vending*) echo "$p $c";; esac; done'

# 结束单个应用后，它的任务卡片应当消失（TaskCleaner 生效）
adb shell dumpsys activity activities | grep -i "taskDescription: label"

# 电池优化白名单是否真的生效（需先 adb root）
adb shell cmd deviceidle whitelist | grep com.dooble.space
```

> **模拟器上跑 adb 的一个硬约束**：MuMu 的 adb daemon 会在两次 Bash 调用之间被回收，
> 而设备同时存在 `127.0.0.1:16384` 与 `emulator-5554` 两个序列号。
> 所以 `start-server` + `connect` + 实际命令**必须写进同一次调用**，
> 并且始终带 `-s 127.0.0.1:16384`，否则会报
> `device not found` 或 `more than one device/emulator`。
>
> 另外 Lawnchair 会把屏幕转成横屏（2560×1440），按竖屏算的坐标全错位。
> 先用 `uiautomator dump` 拿 `bounds` 再点，并
> `settings put system user_rotation 0` + `accelerometer_rotation 0` 锁定竖屏。

在 MuMu 模拟器上的实测结论见 [07-本地测试与模拟器适配.md](07-本地测试与模拟器适配.md)。
