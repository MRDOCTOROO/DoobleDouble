# 09 · 应用安装、宿主克隆与实测结果

本文覆盖「怎么把应用装进空间」这件事的全部路径，以及 2026-09-29 在 MuMu 上
逐项实测的结论。**踩到的三个坑都写在这里**，其中两个已修，一个需要容器侧补丁。

---

## 1. 两条安装路径，用错了会很别扭

| 路径 | 入口 | 适用 | 不适用 |
|---|---|---|---|
| **从文件装入 APK** | 空间详情 → `从文件装入 APK`（SAF 选择器） | 手头有独立 APK 的场景；开源应用从 F-Droid / 官网直链拿到的包 | AAB 拆分包应用（只有一个基础包，装进去缺资源） |
| **从已安装应用导入** | 空间详情 → `从已安装应用导入` | 宿主上已经装好的应用（免存储权限、免导出 APK） | 宿主上没装的应用；AAB 拆分包同样只装基础包（见第 3 节） |

两条路的引擎实现完全不同：

```
从文件：  engine.installApk(spaceId, apk: File)
            └─ core.installPackageAsUser(apk, userId)          // InstallOption.installByStorage

克隆：    engine.installHostApp(spaceId, packageName)
            └─ core.installPackageAsUser(packageName, userId)  // InstallOption.installBySystem
                 └─ getPackageManager().getPackageInfo(pkg, 0)
                      .applicationInfo.sourceDir               // ← 只取了这一个字段
```

**关键差异**：克隆路径不需要存储权限——容器自己就是宿主，直接读 `sourceDir`。
但它也因此**只拿到了基础 APK**（见第 3 节）。

## 2. 坑一：系统应用永远不显示（已修）

### 症状

打开「从已安装应用导入」，标题写着「共 0 个可导入应用」，列表空的。
在 MuMu 这类设备上尤其明显——第三方应用只有一两个，列表看起来像坏了。

### 根因

`HostAppScanner.scan()` 的签名是：

```kotlin
suspend fun scan(
    includeSystem: Boolean = false,     // ← 默认 false
    onlyGmsDependent: Boolean = false,
    query: String = "",
)
```

而 `SpaceViewModel.scanHostApps()` 只传了 `query`：

```kotlin
DoobleContainer.hostScanner.scan(query = query)   // includeSystem 取默认值 false
```

于是系统应用**永远**被过滤掉。讽刺的是 `HostImportSheet` 里「系统应用」这个
筛选芯片的渲染代码早就写好了——它从来没有机会显示。

### 修法

在导入面板加了两个开关（`HostImportSheet` + `SpaceViewModel.setHostFilters`）：

| 开关 | 作用 |
|---|---|
| 包含系统应用 | `includeSystem = true`，把预装的浏览器 / 相机 / 图库等放出来 |
| 只看依赖 GMS | `onlyGmsDependent = true`，按 `requestedPermissions` 里有没有 `com.google.android.gms.*` / `com.android.vending.*` / `com.google.android.c2dm.permission.RECEIVE` 过滤 |

两个开关合并成一个 `setHostFilters(includeSystem, onlyGmsDependent)` 入口，
而不是两个独立函数——它们共享「当前搜索词」这份上下文，分开写必然出现
「改了一个忘了传另一个」。

`scanHostApps` 会把搜索词记进 `hostQuery`，切换开关时用它重扫；
否则用户输入 "camera" 再打开「包含系统应用」，列表会突然退回全量结果，
搜索词看起来"失效了"。

**实测**：打开开关后从 `共 0 个` 变成 `共 65 个`（MuMu 上共 73 个包，
减去宿主自己和 7 个无 `applicationInfo` 的包）。

## 2.5 坑一之二：列表仍然为空 —— 包可见性被 ROM 拦截

### 症状

开关都打开了，列表还是很少甚至空的。用户去系统设置里手动给"读取应用列表"
权限才恢复。

### 根因

Android 11（API 30）起 `getInstalledPackages()` **只返回对调用方可见的包**。
正规做法是声明 `QUERY_ALL_PACKAGES` —— 它是 normal 权限、安装即授予，本该够用。

但 MIUI / ColorOS / OriginOS / EMUI 把它改成了**用户开关**
（设置里叫「读取应用列表」/「获取应用列表」），默认关闭。
关着的时候那个 API 只返回本应用自己。

### 修法：两条腿走路

**① 能绕就绕 —— manifest 里声明 `<queries>`**

```xml
<queries>
    <intent>
        <action android:name="android.intent.action.MAIN" />
        <category android:name="android.intent.category.LAUNCHER" />
    </intent>
</queries>
```

这段走的是 **intent 解析**，不受"读取应用列表"开关影响。
声明之后 `queryIntentActivities(MAIN/LAUNCHER)` 能看到全部有桌面图标的包。

`HostAppScanner.scan()` 因此改成两段：

```kotlin
val primary = packages.mapNotNull { toInfo(it) }        // 主路径
val launcherPackages = launcherPackageNames()            // 基准线
val verdict = HostAppRules.visibilityVerdict(primary.size, launcherPackages.size)
val merged = if (verdict.gated) {
    // 用 launcher 那条路补齐缺失的（getPackageInfo 对它们是允许的，
    // 因为它们匹配了 <queries>）
    HostAppRules.mergeDistinct(primary, extraFromLauncher)
} else primary
```

**② 绕不过就引导 —— UI 给出跳转入口**

`<queries>` 看不到**没有桌面图标**的应用：后台服务、插件，
以及宿主上的 GMS / Play 商店这类系统应用。这些必须用户去开权限。

判据用的是**确定的证据**而不是阈值：

```kotlin
fun visibilityVerdict(visibleCount: Int, launcherCount: Int) =
    VisibilityVerdict(gated = launcherCount > visibleCount, ...)
```

launcher 能看到 100 个、`getInstalledPackages` 只给 1 个 —— 那就一定是被拦了。
比"少于 N 个就报警"可靠得多：一台干净的测试机本来就可能只有十几个应用。

> 注意 `launcherCount == 0` 时返回 `gated = false`。那是查询本身失败，
> 不能据此断言"被拦截"，否则会给用户一个查不出原因的引导。

引导入口由 `AppListAccess.guideIntents()` 构造，策略是
**候选列表 + 逐个 `resolveActivity` 探测**，最后一定兜底到
`ACTION_APPLICATION_DETAILS_SETTINGS`（所有 Android 都支持）。

各 ROM 的设置页组件名随版本反复变，没有任何一个可靠，所以：

| ROM | 候选（按优先级） |
|---|---|
| MIUI / 澎湃 | `com.miui.securitycenter/...PermissionsEditorActivity` 等 3 个 |
| ColorOS | `com.coloros.securitypermission/...PermissionGroupsActivity` 等 3 个 |
| OriginOS | `com.vivo.permissionmanager/...PurviewTabActivity` 等 3 个 |
| EMUI / 鸿蒙 | `com.huawei.systemmanager/...MainActivity` 等 3 个 |
| One UI | `com.samsung.android.lool/...BatteryActivity` 等 2 个 |
| 其它 | 无（只给系统标准入口） |

探测不过的候选**不会**出现在界面上 —— 点了没反应的按钮比没有按钮更糟。
从设置页返回时 `ON_RESUME` 会自动重扫（`SpaceViewModel.onReturnedFromSettings`）。

**相关文件**：`AppListAccess.kt`、`HostAppScanner.kt`、`HostAppRules.visibilityVerdict`、
`GmsSlotPanel.AppListAccessBanner`、`AndroidManifest.xml`

## 3. 坑二：拆分包应用只装进去一个基础包（**未修**）

### 事实

`BlackBoxCore.installPackageAsUser(String packageName, int userId)`：

```java
PackageInfo packageInfo = getPackageManager().getPackageInfo(packageName, 0);
return getBPackageManager().installPackageAsUser(
        packageInfo.applicationInfo.sourceDir,      // ← 只有基础 APK
        InstallOption.installBySystem(), userId);
```

`applicationInfo.splitSourceDirs` **没有被传下去**。

### 后果

2019 年之后上架 Google Play 的应用基本都是 AAB 拆分包（一个基础 APK +
按 ABI / 密度 / 语言拆分的配置 APK）。只装基础包的结果是：资源表里
缺密度目录、缺 native 库，启动时抛 `Resources$NotFoundException` 或
`UnsatisfiedLinkError`。

**这一条直接影响「克隆谷歌系列应用」**——Google 自家的应用
（Maps / Chrome / YouTube / Photos）全是 AAB 拆分包，克隆进去必然不完整。

### 之前文档里的说法是错的

`HostImportSheet` 原来的说明写着：

> 带「拆分包」标记的应用（AAB 分发）也能完整还原，这是手工挑 APK 文件做不到的。

**这句话与引擎实际行为不符**，已改掉。现在列表里的「拆分包」芯片用警示色，
文案是「拆分包 N 项 · 仅装基础包」。

### 正确的修法（需要容器侧补丁，已定位到 4 个改动点）

先说一个容易踩的误判：Bcore 源码树里那份
`Bcore/src/main/java/android/content/pm/PackageParser.java`
**是桩类**，所有方法体都是 `throw new RuntimeException("Stub!")`。
它存在的唯一目的是提供 `Package` / `PackageLite` 的**字段布局**给反射用。
真正干活的是系统自带的 `PackageParser`，由 `PackageParserCompat` 通过
`BRPackageParserMarshmallow` 等反射包装类调用，而调用的签名是
`parsePackage(File, int)` —— **单文件解析，没有拆包入口**。

所以「结构上支持拆包」这个说法只对了一半：字段在，解析、复制、加载三条链路
一处都没接。全量改动点是 **4 个**：

| # | 位置 | 现状 | 要改成 |
|---|---|---|---|
| 1 | `PackageParserCompat.parsePackage` → `parserApk` | 只解析基础 APK | 把宿主 `ApplicationInfo.splitSourceDirs` 里的每个 split 也 `parsePackage` 一遍，把结果填进基础 `Package` 的 `splitCodePaths` / `splitNames`（拆包名从文件名 `split_config.<name>.apk` 或 manifest 的 `split=` 属性取） |
| 2 | `CopyExecutor.exec` | 只 `copyFile(baseCodePath)` | `FLAG_SYSTEM` 分支下 split 保持在系统路径即可（`/data/app/<pkg>/` 下的 APK 是 0644，可读）；`FLAG_STORAGE` 分支要把每个 split 也复制进 `BEnvironment.getBaseApkDir(pkg)` |
| 3 | `BActivityThread.getClassLoader` | `new PathClassLoader(appInfo.sourceDir, ...)` | `PathClassLoader` 的 `dexPath` 本来就接受 **`File.pathSeparator` 分隔的路径列表**。把 `sourceDir` 与 `splitSourceDirs` 用 `File.pathSeparator` 拼起来传进去即可，改动量最小的一条 |
| 4 | `PackageManagerCompat:380` | `addAssetPath(ps.pkg.baseCodePath)` | 对每个 split 再 `addAssetPath` 一次（系统自己就是这么做的），否则资源表里缺密度/语言目录，启动抛 `Resources$NotFoundException` |

**第 3、4 条是「装进去能跑」的必要条件**，第 1、2 条决定「装进去的东西完不完整」。
只做 1+2 会得到一个"文件都在但类加载不到"的诡异状态。

补丁形态与既有的 4 个补丁一致（`tools/bcore-patch/0005-*.patch`，
`build-bcore.sh` 幂等应用），零风险原则不变：**只在拿到多路径时才走新分支，
单 APK 路径行为与上游逐字节等价**。

> **成本提示**：改完要重编 `engine/libs/bcore.aar`（JDK 21 + NDK 29，
> 见 `tools/build-bcore.sh`），再重编宿主。这是本工程最重的一条构建链路。

> **另一个前置条件**：即便补丁做完，**还得先能拿到 Google 应用的 APK**。
> 当前 APKMirror / APKPure 都是 Cloudflare 403，APKCombo 无静态直链
> （见第 6 节）。可行的取得方式只有两条：宿主上已经装了（走克隆路径），
> 或者用容器内已装好的 Aurora Store 登录 Google 账号后从 Play 拉
> —— 而 Aurora Store 走 `PackageInstaller.Session`，落下来的同样是拆分包，
> 又回到这个补丁上。**所以这个补丁是「谷歌系列应用能跑」的唯一卡点。**

## 3.5 容器内安装的实测进展（2026-09-30，MuMu）

### 意图式安装已打通（补丁 `0010`）

**根因**：`ComponentUtils.isRequestInstall(Intent)` 原来只认
`intent.getType() == "application/vnd.android.package-archive"`。Aurora 的
「原生安装程序」下载完成后发的是：

```
act=android.intent.action.INSTALL_PACKAGE
dat=content://com.aurora.store.fileProvider/...   ← 不带 MIME type
```

于是 `isRequestInstall` 返回 false → 容器不拦截 → 意图转发给系统
`com.android.packageinstaller/.InstallStart` → 系统侧查不到虚拟包名的
installerPackageName → 报
`The given installer package name com.aurora.store is invalid`。

**修法**（`tools/bcore-patch/0010-install-action-recognition.patch`）：
`isRequestInstall` 增加 `Intent.ACTION_INSTALL_PACKAGE.equals(intent.getAction())`
判定。已验证：Aurora 原生安装程序下载完 KISS Launcher 后，
`CommonStub` 拦截到 `ACTION_INSTALL_PACKAGE`，容器执行
`installPackageAsUser` → `onPackageInstalled: fr.neamar.kiss, userId: 1`，
`install-events.jsonl` 记录 `"ok":true,"message":"已装入当前空间"`。

### Aurora 的安装器选择（重要）

Aurora 设置 →「安装」→「安装方式」有两个选项：

- **会话安装器**（默认）：走 `PackageInstaller.Session`。在 MuMu 上，
  `openWrite` 直写文件已由补丁 `0009` 修复 EBADF，但**随后卡在
  `Failed to execute fsync() across bridge`**——libhoudini（ARM 翻译层）
  无法对宿主进程打开的文件描述符执行 `fsync`。这是 MuMu 模拟器的限制，
  真机上不会出现。
- **原生安装程序（已废弃）**：基于 intent 的安装包。配合补丁 `0010`，
  **在 MuMu 上实测可用**（KISS Launcher 安装成功）。

**结论**：在 MuMu 上请把 Aurora 的「安装方式」切到
「原生安装程序（已废弃）」。会话安装器在 MuMu 上受 fsync 桥接限制。

### 启动路由：F-Droid 打开成「计算器」（补丁 `0011`，已修）

F-Droid 在 manifest 里把「防偷看」的伪装入口（`CalculatorActivity`，一个
计算器）声明为**第一个** `MAIN/LAUNCHER` activity。容器的
`BPackageManager.getLaunchIntentForPackage` 取 `ris.get(0)`，于是从桌面点
F-Droid 打开的是计算器，看起来像装了个假应用。

**修法**（`tools/bcore-patch/0011-launch-intent-label-preference.patch`）：
解析结果多于一个时，优先选择「activity 解析出来的 label 与应用名一致」
的入口（真实入口 label 为空时回落到应用名；伪装入口带自己的 label）。
已验证：F-Droid 打开的是真实界面。

## 4. 坑三：权限白名单不含 CAMERA / 定位（已定位，未修）

### 现象

把宿主预装的**相机**（`com.android.camera2`）克隆进空间后启动：

- 应用**确实跑起来了**——容器虚拟进程存在、任务卡片显示「相机」+ 真图标、
  `PermissionsActivity` 正常创建、权限弹窗正常弹出并授权成功；
- 但应用自己弹「相机发生错误 / 此应用缺少运行所需的必要权限」，进不了取景界面。

**对照组**：在宿主上直接启动同一个相机，正常显示首次运行引导页。
所以问题在容器侧，不是模拟器没有相机。

### 根因（部分定位）

Bcore 的权限钩子是一份**白名单**，命中就直接返回 `PERMISSION_GRANTED`：

| 位置 | 放行的权限 |
|---|---|
| `IActivityManagerProxy.checkPermission` | `ACCOUNT_MANAGER`、`SEND_SMS`、音频类、存储/媒体类 |
| `IPackageManagerProxy.checkPermission` / `checkSelfPermission` | 同上 + 通知/Xiaomi 类 |

`isAudioPermission()` 里的清单是：`RECORD_AUDIO`、`CAPTURE_AUDIO_OUTPUT`、
`MODIFY_AUDIO_SETTINGS`，以及 `FOREGROUND_SERVICE_{MICROPHONE,MEDIA_PROJECTION,
CAMERA,LOCATION,HEALTH,DATA_SYNC,SPECIAL_USE}`。

**`android.permission.CAMERA` 和 `ACCESS_FINE/COARSE_LOCATION` 都不在名单里**，
于是落到 `method.invoke(who, args)` —— 真实系统校验，参数里的包名是
**虚拟包名**（`com.android.camera2`）。

### 已排除的可能

- **不是宿主缺权限**：`dumpsys package com.dooble.space.debug` 确认
  `CAMERA: granted=true`、`RECORD_AUDIO: granted=true`。
- **不是权限请求没到系统**：`GrantPermissionsViewModel` 日志显示
  两个弹窗都点了允许，`uid=10051 package=com.dooble.space.debug`。
- **不是任务栈缓存**：`force-stop` 后冷启动，现象一致。
- **`replaceLastUid` 本身是对的**：它把 `BlackBoxCore.getBUid()` 换成
  `getHostUid()`，而宿主 uid 确实有 CAMERA。

所以怀疑点落在 `IPackageManagerProxy.CheckSelfPermission` 的兜底分支上——
它没有做包名替换，把虚拟包名直接交给了系统去查。给
`com.android.camera2` 也 `pm grant` 定位权限后现象依旧，说明可能还有
第二重因素（例如 `onRequestPermissionsResult` 的投递）。

### 建议的修法

在 `isAudioPermission()` 之外补一个 `isCameraOrLocationPermission()`，
把 `CAMERA`、`ACCESS_FINE_LOCATION`、`ACCESS_COARSE_LOCATION`、
`ACCESS_BACKGROUND_LOCATION`、`FOREGROUND_SERVICE_LOCATION` 加进白名单，
与既有的「音频/存储一律放行」保持同一策略。

**注意这是隐私相关的取舍**：白名单命中等于**不经用户确认直接放行**。
现有代码已经这么处理音频与存储了，加相机/定位属于同一类决定，
但应当是有意识的决定，而不是漏加。

## 6. 去哪里找测试 APK

| 源 | 自动化下载 | 说明 |
|---|---|---|
| **F-Droid** | ✅ 可用 | 直链 `https://f-droid.org/repo/<包名>_<versionCode>.apk`；API `https://f-droid.org/api/v1/packages/<包名>` 给版本号。**注意 API 不返回文件名**，要按约定自己拼 |
| **GitHub Releases** | ✅ 可用 | 项目自己发布的 APK |
| 应用官网直链 | ✅ 可用 | 例如 Telegram 的 `https://telegram.org/dl/android/apk` |
| APKMirror | ❌ 403 | Cloudflare 人机校验 |
| APKPure | ❌ 403 | 同上 |
| APKCombo | ⚠️ 页面可达 | 下载链接由 JS 动态生成，HTML 里没有静态直链 |

> **F-Droid API 的坑**：`/api/v1/packages/<pkg>` 返回的条目只有
> `versionName` 和 `versionCode`，**没有 `apkName`**。
> 按 `apkName` 去找会全部拿到 `null` 然后静默跳过。
> 正确做法是拼 `https://f-droid.org/repo/{packageName}_{versionCode}.apk`。
