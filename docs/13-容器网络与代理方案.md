# 13 · 容器网络与代理方案（含真机排查指引）

本文记录「容器内应用无法连接外网」的排查结论、Bcore 网络代理钩子的现状与
修复（补丁 0015），以及「在容器内安装 Clash 类代理让 microG 正常工作」的
可行性评估与实施步骤。

---

## 1. 容器网络架构：没有独立网络栈

Bcore 容器**不创建网络命名空间**。空间内的虚拟应用跑在宿主的进程里
（同一 UID、同一网络栈），所以：

- 容器应用的 socket 与宿主进程走同一条网络路径；
- 宿主能访问的网络，容器应用**原则上**也能访问；
- 宿主 VPN（TUN）/ 全局 http_proxy 对容器应用同样生效。

因此「容器内应用无法连接外网」通常不是容器隔离出来的问题，而是
**容器拿到的网络信息与真实网络不一致**，或**宿主代理没有覆盖到容器进程**。

---

## 2. Bcore 网络相关钩子的现状

Bcore 默认注入 `IConnectivityManagerProxy`、`INetworkManagementServiceProxy`、
`IVpnManagerProxy`（Android 12+）、`IWifiManagerProxy` 等网络代理。其中
`IConnectivityManagerProxy` 的行为对「容器内应用看网络」影响最大：

| 钩子 | 上游行为 | 风险 |
|---|---|---|
| `getActiveNetwork` / `getNetworkInfo` / `getAllNetworks` | 先透传真实结果，为空/异常时返回**伪造的**「WIFI 已连接」 | 设备真没网时，应用以为有网，表现为「一直连接中」 |
| `getLinkProperties` / `createLinkProperties` | 真实结果为空时，构造带 `8.8.8.8/8.8.4.4` 的假 LinkProperties | 同上 |
| `getDnsServers` | **无条件返回 `8.8.8.8/8.8.4.4`**，不先问真实系统 | 在 Google DNS 不可达的网络里，调用方 DNS 解析失败 |
| `getNetworkCapabilities` | 给真实结果追加 `NET_CAPABILITY_NOT_VPN` / `NOT_RESTRICTED` | 让应用以为「不是 VPN」，语义失真 |
| `isNetworkValidated` | 恒返回 `true` | 应用以为网络已通过验证 |
| `registerNetworkCallback` 等 | 透传，失败返回 0 | 低 |

`IDnsResolverProxy` 由于 `getWho()` 返回 `null`，在 `ClassInvocationStub.injectHook()`
里会**提前 return**——也就是说 `dnsresolver` 服务实际上**没有被替换**，
容器内 `DnsResolver` 走的是真实系统服务。这一点是好的，不要试图「修复」它：
一旦启用该代理，反而可能把正常的系统 DNS 解析拦截掉。

### 2.1 已修复：`getDnsServers` 硬编码 Google DNS（补丁 0015）

`ConnectivityManager.getDnsServers()`（`@SystemApi`，部分网络工具/诊断应用会
通过反射调用）在容器内被 `GetDnsServers` 钩子拦截，上游实现**无条件**返回
`8.8.8.8/8.8.4.4`。在 Google DNS 不可达的网络（国内运营商环境、公司内网）里，
这类应用的 DNS 查询会全部失败，表现为「容器内应用无法连接外网」。

补丁 `0015-dns-delegate-real-system.patch` 改为：

1. 优先透传真实系统 DNS（`method.invoke(who, args)`）；
2. 失败时从真实活动网络的 `LinkProperties.getDnsServers()` 读取；
3. 仍失败才返回空列表——**绝不硬编码 Google DNS**。

## 3. 真机排查：容器内应用无法连接外网

按顺序做以下检查，每步都有明确结论：

### 3.1 先确认宿主本身有没有网

在设备上（通过 adb）：

```bash
adb shell "curl -s -o /dev/null -w '%{http_code}' https://www.baidu.com"
# 200 = 设备有网；000 = 设备本身没网
```

如果宿主没网，容器当然也没网，问题在设备网络/热点，不在容器。

### 3.2 用应用内自检定位

打开 Dooble → 空间 → 自检（GmsSelfCheck）。NetworkProbe 会给出四个结论之一：

| 结论 | 含义 | 处理 |
|---|---|---|
| `OK` | 国内外 + checkin 都通 | 网络没问题，问题在别处 |
| `CHECKIN_BLOCKED` | Google 通用端点通，但 `android.clients.google.com` 不通 | 代理规则漏了 checkin 域名，见 NetworkProbe 建议 |
| `GOOGLE_BLOCKED` | 国内通、Google 不通 | 代理没生效 / 被墙 |
| `NO_NETWORK` | 国内也不通 | 设备没有可用网络，或被系统限制联网 |

### 3.3 检查宿主代理是否覆盖容器

容器应用与宿主同 UID（`com.dooble.space.debug`）。如果你的代理是**分应用模式**
（如 Clash 只给白名单应用走代理），必须把宿主包加进代理名单，否则容器流量
会绕过代理直连，Google 全部失败。

```bash
# 查看当前全局 http_proxy（代理模式应看到值，TUN 模式通常为空）
adb shell settings get global http_proxy

# 查看活动网络是否 VPN（TUN 模式应看到 VPN 网络）
adb shell dumpsys connectivity | grep -i "Active default network" -A2
adb shell dumpsys connectivity | grep -i vpn
```

| 场景 | 期望 |
|---|---|
| Clash TUN 模式 | `Active default network` 指向 VPN；宿主包在代理名单里 |
| Clash 代理模式 | `http_proxy` 非空，指向 Clash 的混合端口 |

### 3.4 检查 DNS

```bash
# 看系统 DNS
adb shell dumpsys connectivity | grep -i dns
adb shell getprop net.dns1

# 实际探测一次 Google 端点
adb shell "curl -s -o /dev/null -w '%{http_code}' https://www.gstatic.com/generate_204"
```

如果 `dumpsys` 里 DNS 正常、但 `curl` 不通，且域名被解析到无关 IP
（NetworkProbe 会提示「DNS 可疑」），说明是 **DNS 污染**：需要让流量走代理
（TUN 或全局 http_proxy），由代理端解析域名。

## 4. 容器内安装 Clash 类代理：可行性评估与实施

### 4.1 结论

| 方案 | 可行性 | 说明 |
|---|---|---|
| **代理模式（HTTP/SOCKS 监听本地端口）+ 全局 http_proxy** | ✅ **可行，推荐** | Clash 作为普通应用跑在容器里，监听 `127.0.0.1:7890`；容器与宿主共享 loopback，microG/Aurora 都能连到它；再把全局 http_proxy 指向它即可。无需改 Bcore |
| **TUN 模式（VpnService）** | ⚠️ 架构支持、需真机实测 | Bcore 的 `establishVpn` 钩子会把容器内 VpnService 的配置指向宿主 `ProxyVpnService` 占位，TUN fd 返回给虚拟应用做包转发。但 `ProxyVpnService` 本身不转发数据，且 Clash for Android 的 VpnService 在容器内的行为未经验证，风险高 |

### 4.2 为什么代理模式可行

- 容器应用与宿主同进程同网络栈，`127.0.0.1` 就是宿主 loopback；
- Clash 以虚拟应用身份在容器内运行，其监听端口绑定在宿主 loopback 上；
- microG / Aurora 遵循 Android 全局 `http_proxy`（AGENTS.md 已确认）；
- 设好全局代理后，HTTPS 请求走 `CONNECT` 隧道，由代理端解析域名，
  **绕开本地 DNS 污染**——这正是 microG checkin 需要的。

### 4.3 实施步骤

前置条件：容器内已装配 microG（见 docs/10），并能打开商店。

1. **把 Clash 类代理 APK 装进容器**：通过商店搜索安装，或「从文件装入 APK」。
   推荐使用支持**代理模式**的版本（Clash Meta for Android 等）。
2. **在容器内启动 Clash**，切到代理模式（关闭 TUN），记下混合端口
   （默认 `7890`）。
3. **设置全局 http_proxy**（需要 adb，真机开启 USB 调试）：

   ```bash
   adb shell settings put global http_proxy 127.0.0.1:7890
   ```

   > Clash 跑在容器内 = 跑在宿主进程 = `127.0.0.1` 可达。全局代理对设备所有
   > 应用生效，包括容器里的 microG / Aurora。

4. **验证**：

   ```bash
   adb shell settings get global http_proxy   # 应为 127.0.0.1:7890
   # 在容器里打开 Dooble 自检，NetworkProbe 应变为 OK / 能连 checkin
   ```

5. **清除代理**（不再需要时）：

   ```bash
   adb shell settings put global http_proxy :0
   ```

### 4.4 注意事项

- **不要默认挂代理**：宿主能直连 Google 时，挂代理反而可能让 Aurora 的
  Play 认证 TLS 握手直接 EOF（`SSLHandshakeException: connection closed`）。
- **TUN 模式慎用**：`ProxyVpnService` 只占位不转发，TUN 建起来但没人读包，
  会让容器内所有应用断网。若确需 TUN，请先真机验证 Clash 的包转发是否生效。
- 代理端口建议固定，避免 Clash 每次随机端口导致 http_proxy 失效。

## 5. 真机验证指引（本轮三项修复）

### 5.1 商店安装状态同步（补丁 0014）

1. 构建并安装最新 APK（含新 AAR）。
2. 在空间里打开 Aurora Store，下载并安装一个应用。
3. 观察：安装过程中商店显示「正在安装中」→ 完成后应**自动变为已安装/可打开**，
   不再需要手动刷新；同时应用出现在容器桌面。
4. 检查日志：

   ```bash
   adb logcat -s PackageInstallerProxy BPackageManagerService
   ```

   预期能看到 `createSession -> ...`、`registerSessionCallback -> ...`，
   以及安装完成日志。
5. 检查安装事件：

   ```bash
   adb shell run-as com.dooble.space.debug cat files/dooble/install-events.jsonl
   ```

   应能看到最近一条会话安装结果为成功。

### 5.2 容器内应用联网（补丁 0015 + 配置）

1. 打开 Dooble 自检，确认 NetworkProbe 结论。
2. 若为 `GOOGLE_BLOCKED` / `CHECKIN_BLOCKED`，按第 3 节排查代理覆盖与 DNS。
3. 若使用代理模式，确认全局 `http_proxy` 已设置（3.3/4.3）。
4. 在容器内打开一个需要联网的应用（如 Aurora Store 搜索页），确认能加载。

### 5.3 容器内 Clash 代理 + microG

1. 按 4.3 装好 Clash 并设置全局代理。
2. 在 microG 登录页（docs/10）执行登录：
   - 容器内打开「登录 Google 账号」；
   - WebView 应能加载 `accounts.google.com`（真机上应能看到登录页内容，
     不再有 MuMu 的 tile 内存限制问题）；
   - 若停在「请稍等…」，抓日志确认 checkin 是否成功：
     ```bash
     adb logcat -s GmsAuthLoginBrowser
     ```
   - 若 `Checkin failed`，回到 3.3 检查代理规则是否覆盖
     `android.clients.google.com`。
