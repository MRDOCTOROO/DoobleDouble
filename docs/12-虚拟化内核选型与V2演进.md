## 1. 为什么会出现这个方向

当前工程的内核是 Bcore（NewBlackbox 分支，VirtualApp 血统）。它解决了：

- 免 Root 多开（Binder 钩子 + 进程伪装）
- 容器内安装路由（补丁 0002 / 0010）
- microG 兼容（签名伪造接入点）
- JobScheduler / WorkManager 派发（补丁 0006 / 0012）

但 Bcore 的痛点是：

1. **上游维护稀疏**：NewBlackbox 上游活跃度一般，新 Android 版本适配靠社区分支；
2. **隐藏 API 依赖**：Android 9+ 的 hidden API 拦截越来越严，容器内部反射频繁踩坑
   （本轮补丁 0012 就是典型案例：`IJobService` 是 @hide 接口，反射被拦）；
3. **拆分包 / AAB 支持缺**：Bcore 的 `installPackageAsUser` 只装基础 APK
   （见 `docs/09` 坑二，4 个改动点至今未落地）；
4. **新特性缺失**：虚拟定位、网络隔离、64 位支持等要么没有要么不完善。

因此用户提出：**能否换内核，或借鉴多个内核，或直接在这些开源项目基础上重做 V2，
或在 App 内部做「内核可切换」的兼容层。**

## 3. 借鉴点分析（不换内核也能吸收）

即使不整体换内核，以下能力也值得**反向移植**进当前 Bcore：

### 3.1 从 SpaceCore 借鉴
- **更干净的进程隔离 / 冷启动路径**：SpaceCore 对 Binder 代理做了模块化，可参考其
  服务代理注册表设计，降低后续加钩子的成本；
- **多用户 / 多空间的性能优化**：如果 SpaceCore 在 `getInstalledPackages` 等热点上有
  缓存思路，可移植到 `BcoreEngine.listApps`（当前已有 label 缓存，可再扩展）。

### 3.2 从 Extendroid 借鉴（注意：它**不是**容器内核）
- Extendroid 是「桌面式多窗口 / 远程访问」管理器，依赖 Shizuku，走系统级窗口能力，
  与「在宿主进程内虚拟 Android 环境」是两条完全不同的技术路线，**不能作为内核候选**；
- 可借鉴的是**产品形态**：多窗口预览、悬浮球控制、熄屏保活——这些是宿主 UI 层可以
  独立实现的交互，不依赖容器内核。若未来做「空间内多窗口」，可参考其交互设计。

### 3.3 从 SPatch 借鉴（注意：它是启动器 UI，不是补丁工具）
- SPatch-Update 核实后是 SlimVXposed 的 **Launcher UI**（`com.android.launcher2` 启动器改），
  并非 APK 静态补丁工具——「用 SPatch 给顽固应用打补丁」的设想**不成立**；
- 但「对导入 APK 做一次性静态补丁（去签名校验 / 去 root 检测 / 去多开检测）」的**思路**
  仍值得在 V2 的导入管线里自研实现，只是不能复用 SPatch 的代码（CC-BY-4.0 仅覆盖其 UI）。

## 4. V2 架构：「内核可切换」的 SPI（**本次已落地**）

当前代码已经具备插件化内核的雏形，本次把它固化成了**正式的工厂 SPI + 注册表**：

```
VirtualEngine（能力接口）
  ▲                          ▲
  │ implements               │ implements
BcoreEngine（src/bcore）   SandboxEngine（降级）
  ▲
  │ create()（反射，AAR 在才可用）
BcoreEngineFactory ────────┐
                            ▼
VirtualEngineFactory（SPI 接口）   ← 新增
  ├── BcoreEngineFactory          （AAR 接入才 available）
  └── SandboxEngineFactory         （永远 available，兜底）
              │ register
              ▼
        EngineRegistry（注册表）    ← 新增
        createFirstAvailable(context) 按注册顺序挑第一个可用引擎
              │
              ▼
        DoobleContainer.bootstrapHost / bootstrap
```

### 4.1 新增文件

| 文件 | 作用 |
|---|---|
| `engine/.../VirtualEngineFactory.kt` | SPI 接口：`id` / `available` / `create(context)` |
| `engine/.../EngineRegistry.kt` | 注册表：`register` / `unregister` / `create(id)` / `createFirstAvailable` / `isAvailable`；`instance` 内置 Bcore + 沙箱 |
| `engine/.../internal/SandboxEngineFactory.kt` | 降级沙箱工厂（永远可用） |

### 4.2 改造点

- `BcoreEngineFactory` 改为实现 `VirtualEngineFactory`（`id = "bcore"`，`create(context)` 忽略 context）；
- `DoobleContainer` 不再硬编码 `BcoreEngineFactory.createOrNull() ?: SandboxEngine()`，
  改为 `EngineRegistry.instance.createFirstAvailable(context)`；
- `BootState.Ready.bcoreBundled` 改走 `EngineRegistry.instance.isAvailable(BcoreEngineFactory.id)`。

### 4.3 如何接入新内核（V2 的「换内核」路径）

```
object MyEngineFactory : VirtualEngineFactory {
    override val id = "my-engine"
    override val available get() = /* 依赖是否接入 */
    override fun create(context: Context) = /* 构造引擎或 null */
}
EngineRegistry.instance.register(MyEngineFactory)   // 注册顺序靠前 = 优先
```

上层（UI / GMS 供给层 / 自检）不感知具体内核——它们只依赖 `VirtualEngine`。

### 4.4 仍待办（不在本次范围）

1. **能力降级矩阵**：某内核不支持的能力（如签名伪造）要显式上报给 UI 隐藏入口；
2. **迁移层**：空间元数据（`SpaceStore`）是引擎无关的，但容器内数据（Bcore 的
   `blackbox/` 目录）与内核强相关，跨内核迁移需要「导出 → 重装 → 数据迁移」；
3. **配置化选择**：目前按注册顺序自动选，未来可支持用户在设置里指定优先内核 id。

> **成本提示**：接入一个新内核 = 写一个工厂 + 重验 microG 链路 + 重验安装路由 +
> 重跑自检。相比早期「重写一遍 `VirtualEngine` 适配」已大幅收敛，但仍是数周级工作量，
> 应作为独立立项推进，而非在 bug 修复周期内并行。

> **结论**：四个候选**没有一个**满足「许可证清晰 + 活跃维护 + 容器内核 + GMS 兼容」。
> 因此 V2 的正确做法不是现在换内核，而是把 `VirtualEngine` SPI 化，让未来出现合格
> 内核时「加一个适配器」即可接入。

## 7. 结论

- **当前阶段不换内核（联网核实后结论更硬）**：Bcore 的补丁体系已解决本工程 90% 的
  核心问题；而四个候选里两个无 LICENSE、一个是 GPL-3.0 多窗口管理器、一个是启动器 UI，
  **没有任何一个能合法、技术上直接替换 Bcore**。换内核会把已验证的 microG / 安装路由 /
  签名伪造全部推倒重来，且引入法律风险。
- **V2 = 把 `VirtualEngine` SPI 化（本次已落地）**：新增 `EngineFactory` SPI 与
  `EngineRegistry` 注册表，让「换内核」从「重写工程」变成「新增一个适配器 + 注册」。
  未来出现合格内核（许可证清晰 + 活跃 + GMS 兼容）时，只需写一个实现并注册。
- **SPatch 思路可以借鉴**：即使不换内核，导入 APK 时做静态补丁（去多开检测 /
  去签名校验）能提升容器兼容性——但注意其 CC-BY-4.0 仅覆盖 UI，补丁逻辑需自研。
