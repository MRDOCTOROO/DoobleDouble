## 1. 为什么会出现这个方向

当前工程的内核是 Bcore（NewBlackbox 分支，VirtualApp 血统）。它解决了：

- 免 Root 多开（Binder 钩子 + 进程伪装）
- 容器内安装路由（补丁 0002 / 0010）
- microG 兼容（签名伪造接入点）
- JobScheduler / WorkManager 派发（补丁 0006 / 0012）

但 Bcore 的痛点是：

1. **上游维护稀疏**：NewBlackbox 上游活跃度一般，新 Android 版本适配靠社区分支；
2. **隐藏 API 依赖**：Android 9+ 的 hidden API 拦截越来越严，容器内部反射频繁踩坑
   （本轮补丁 0012 就是典型案例：`IJobService` 是 @hide 接口，反射被拦）；
3. **拆分包 / AAB 支持缺**：Bcore 的 `installPackageAsUser` 只装基础 APK
   （见 `docs/09` 坑二，4 个改动点至今未落地）；
4. **新特性缺失**：虚拟定位、网络隔离、64 位支持等要么没有要么不完善。

因此用户提出：**能否换内核，或借鉴多个内核，或直接在这些开源项目基础上重做 V2，
或在 App 内部做「内核可切换」的兼容层。**

## 2. 候选内核速览（基于既有知识，**需联网核实**）

| 项目 | 血统 | 定位 | 已知优点 | 已知风险 / 不确定点 |
|---|---|---|---|---|
| **Bcore / NewBlackbox**（当前） | VirtualApp 分支 | 免 Root 多开 | 已被本工程深度改造，补丁集完整；microG 链路已通 | 上游维护稀疏；hidden API 适配要自己补；AAB 拆分包缺 |
| **FSpaceCore/SpaceCore** | VirtualApp 分支，现代化重写 | 高性能多开核心 | 对 Android 12+ 适配积极；性能优化；社区活跃 | 与本工程的补丁体系不兼容；microG / 签名伪造要重新验证；license 待核实 |
| **ServenScorpion/VirtualApp** | 原版 VirtualApp 的维护分支 | 经典多开 | 资料多、文档全；API 稳定；大量二次开发案例 | 新 Android 版本支持滞后；Binder 钩子被 ROM 反制风险 |
| **legendsayantan/Extendroid** | VirtualApp 增强分支 | 多开 + GMS 兼容增强 | 明确针对 GMS / 谷歌环境做过增强，与本工程目标契合 | 维护活跃度待核实；hidden API / 新版本适配待核实 |
| **Katana-Official/SPatch-Update** | APK 补丁工具（非容器） | 应用侧打补丁 | 可让普通应用支持多开 / 去签名校验 / 改行为，配合容器使用 | 不是「容器内核」本身，属于互补工具；使用方式 / license 待核实 |

> **关键区分**：前四个是「容器内核」（在宿主进程里虚拟出一个 Android 环境），
> SPatch 是「对 APK 本身做静态补丁」（改掉应用的签名校验、多开限制等）。
> 两者可以**叠加使用**：容器负责运行环境，SPatch 负责让某些顽固应用愿意在容器里跑。

## 3. 借鉴点分析（不换内核也能吸收）

即使不整体换内核，以下能力也值得**反向移植**进当前 Bcore：

### 3.1 从 SpaceCore 借鉴
- **更干净的进程隔离 / 冷启动路径**：SpaceCore 对 Binder 代理做了模块化，可参考其
  服务代理注册表设计，降低后续加钩子的成本；
- **多用户 / 多空间的性能优化**：如果 SpaceCore 在 `getInstalledPackages` 等热点上有
  缓存思路，可移植到 `BcoreEngine.listApps`（当前已有 label 缓存，可再扩展）。

### 3.2 从 Extendroid 借鉴
- **GMS 兼容增强**：Extendroid 明确做了 GMS 相关适配，可对照它的钩子清单，
  补齐 microG 在容器内的坑（账号、推送、认证）；
- **Play 服务绑定的处理**：容器内应用 bind GmsCore 的路径，值得对照。

### 3.3 从 SPatch 借鉴
- **对顽固应用做静态补丁**：比如某些应用检测多开环境就退出，可以用 SPatch 思路
  在导入 APK 时做一次性补丁（去签名校验 / 去 root 检测 / 去多开检测）；
- **拆分包补丁**：SPatch 有处理 AAB 拆分的经验，可参考其拆分合并逻辑。

## 4. V2 架构建议：「内核可切换」的兼容层

当前代码其实**已经具备**插件化内核的雏形：

```
VirtualEngine（接口）
 ├── BcoreEngine（编译期绑定 Bcore，AAR 存在才编译）
 └── SandboxEngine（降级，无容器能力）
BcoreEngineFactory：反射探测，createOrNull() 失败则降级
```

要支持「内部切换不同内核」，需要把这条链做成**运行时多实现**：

1. **内核 SPI**：把 `VirtualEngine` 拆成更细的能力接口（安装 / 启动 / 包管理 /
   进程 / 签名 / JobScheduler），每个内核按能力实现，而不是全有或全无；
2. **内核注册表**：`EngineProvider` 按编译期声明的实现列表 + 运行期探测结果，
   选择一个可用内核（Bcore / SpaceCore / Extendroid…）；
3. **能力降级矩阵**：某内核不支持的能力（如 SpaceCore 的签名伪造）要显式上报，
   UI 按能力隐藏入口，而不是假装存在；
4. **迁移层**：空间元数据（`SpaceStore`）是引擎无关的，但容器内数据
   （Bcore 的 `blackbox/` 目录）与内核强相关。跨内核迁移需要「导出 → 重装 → 数据迁移」。

> **成本提示**：接入一个新内核 = 重写一遍 `VirtualEngine` 适配 + 重验 microG 链路
> + 重验安装路由 + 重跑自检。这是数周级工作量，建议作为 V2 单独立项，
> 而非在 v0.1/v0.2 的 bug 修复周期内并行推进。

## 7. 结论

- **当前阶段不换内核**：Bcore 的补丁体系已经解决了本工程 90% 的核心问题，
  换内核会把已验证的 microG / 安装路由 / 签名伪造全部推倒重来。
- **但必须为 V2 铺路**：把 `VirtualEngine` 进一步 SPI 化，让「换内核」从
  「重写工程」变成「新增一个适配器」。
- **SPatch 思路可以立即借鉴**：即使不换内核，导入 APK 时做静态补丁
  （去多开检测 / 去签名校验）能显著提升容器兼容性。
