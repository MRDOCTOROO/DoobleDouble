# 架构设计

## 一、进程模型

```
┌─────────────────────────────────────────────────────────────┐
│  :main  宿主主进程（UI）                                      │
│   DoobleApp / MainActivity / Compose UI                      │
└──────────────┬──────────────────────────────────────────────┘
               │ 同进程调用（引擎 API）
┌──────────────▼──────────────────────────────────────────────┐
│  :main  引擎层（SandboxEngine 就在这个进程）                   │
│   空间元数据 / APK 装载 / 谷歌环境编排                          │
└──────────────┬──────────────────────────────────────────────┘
               │ Binder
┌──────────────▼──────────────────────────────────────────────┐
│  :server  VAServer（接入真引擎后才存在）                       │
│   虚拟包管理 / 虚拟 userId 分配 / 虚拟进程调度                   │
└──────────────┬──────────────────────────────────────────────┘
               │ fork
┌──────────────▼──────────────────────────────────────────────┐
│  :p0 … :pN  虚拟应用进程                                       │
│   每个进程 = (空间, 包名, 进程名) 三元组                        │
│   进程内已安装 IO 重定向 hook，看到的文件系统是空间的            │
└─────────────────────────────────────────────────────────────┘
```

**关键点**：虚拟应用进程**不是**独立 App 进程，而是宿主 App 的附属进程。
所以：
- 系统只认为 Dooble Double 一个应用在跑；
- 虚拟应用拿不到真实 uid，权限以宿主为准（因此宿主申请的权限要覆盖虚拟应用需求）；
- 虚拟应用之间靠 `(spaceId, packageName)` 隔离，而不是靠 uid。

## 二、隔离维度

| 维度 | 隔离手段 | 实现位置 |
|---|---|---|
| 包可见性 | Hook PackageManagerService，按空间过滤 `getInstalledPackages` | 引擎（Bcore） |
| 应用私有数据 | IO 重定向 `/data/data/<pkg>` → `<space>/data/<pkg>` | `native/io_redirect.cpp` |
| 外部存储 | IO 重定向 `/sdcard` → `<space>/sdcard` | `native/io_redirect.cpp` |
| SharedPreferences / 数据库 | 随私有数据一起被重定向 | 同上 |
| AccountManager | 代理 Binder 调用，按空间返回账号列表 | 引擎（Bcore） |
| 设备指纹 | 覆盖 `Build.*` 静态字段与 `ro.product.*` 属性 | `gms/DeviceProfileSpoofer` + native |
| 包签名 | PMS Hook 返回伪造签名 | `gms/GmsSignatureSpoof` + 引擎 |
| 定位 | 拦截 LocationManager | 引擎（待实现） |

## 三、谷歌环境装配时序

```
用户点「装配谷歌环境」
        │
        ▼
┌───────────────────────────────────────────────┐
│ 1. 能力前置校验                                │
│    engine.capability.supportsSignatureSpoof ? │
│    ✗ → 直接失败，明确告知原因（不做无用下载）    │
└───────────────────┬───────────────────────────┘
                    ▼
┌───────────────────────────────────────────────┐
│ 2. 逐个组件解析 APK（三级回退）                 │
│    ① assets/microg/<name>.apk    （离线内置）  │
│    ② files/dooble/gms-cache/<name>.apk（缓存） │
│    ③ 远端下载（3 个镜像依次回退）               │
│    每级都做 ZIP 魔数 + AndroidManifest 校验     │
└───────────────────┬───────────────────────────┘
                    ▼
┌───────────────────────────────────────────────┐
│ 3. 以系统应用身份装入空间                       │
│    GmsCore(com.google.android.gms)  必需       │
│    FakeStore(com.android.vending)   必需       │
└───────────────────┬───────────────────────────┘
                    ▼
┌───────────────────────────────────────────────┐
│ 4. 下发签名伪造策略                             │
│    <space>/data/.dooble/spoof_policy.json      │
│    → 容器 PMS Hook 读取并建立映射表             │
└───────────────────┬───────────────────────────┘
                    ▼
┌───────────────────────────────────────────────┐
│ 5. 下发设备指纹                                 │
│    <space>/data/.dooble/device_profile.json    │
│    → native 层逐条覆盖 Build / SystemProperties │
└───────────────────┬───────────────────────────┘
                    ▼
┌───────────────────────────────────────────────┐
│ 6. 自动跑一次自检，把结果推给 UI                 │
└───────────────────────────────────────────────┘
```

**第 4 步和第 5 步是分水岭。** 缺第 4 步 → 应用提示「Google Play 服务不可用」；
缺第 5 步 → 登录时报 `12500` 或提示设备未认证。

## 四、签名伪造的落盘格式

`<space>/data/.dooble/spoof_policy.json`：

```json
{
  "enabled": true,
  "version": 3,
  "targets": [
    { "packageName": "com.google.android.gms",  "sha1": "38918a453d07199354f8b19af05ec6562ced5788", "provider": "microG" },
    { "packageName": "com.google.android.gsf",  "sha1": "38918a453d07199354f8b19af05ec6562ced5788", "provider": "microG" },
    { "packageName": "com.android.vending",     "sha1": "38918a453d07199354f8b19af05ec6562ced5788", "provider": "microG" },
    { "packageName": "com.google.android.maps", "sha1": "38918a453d07199354f8b19af05ec6562ced5788", "provider": "microG" }
  ]
}
```

容器 native/PMS Hook 启动时读这个文件建表。**不要改这些 SHA-1** ——
应用侧内置的就是这几个哈希，写错等于没做伪造。

## 五、Native 层设计

### 5.1 PLT Hook（`plt_hook.cpp`）

```
hook_plt_all(symbol, replacement, &original)
    │
    ├─ dl_iterate_phdr 枚举所有已加载模块
    │
    ├─ 对每个模块：
    │    解析 PT_DYNAMIC → DT_STRTAB / DT_SYMTAB / DT_JMPREL / DT_RELA / DT_REL
    │    ├─ 遍历 .rela.plt，匹配符号名
    │    └─ mprotect(GOT 所在页, RW) → 改写 GOT 表项
    │
    └─ 原函数地址回填到 original，替身函数里用 dlsym(RTLD_NEXT) 转调
```

**已知局限（诚实说明）**：

1. 只拦得住**通过 PLT/GOT 调用**的场景。若调用方用 `dlsym` 拿到地址后直接 `blr`，拦不到；
2. Android 6+ 默认开启 packed relocations（APS2 压缩格式），此时 `DT_JMPREL` 可能为空，
   本实现会失效。生产环境建议引入 **Dobby / xDL** 做 inline hook（`CMakeLists.txt` 已预留开关）。

### 5.2 IO 重定向（`io_redirect.cpp`）

被 Hook 的函数：`open`、`openat`、`access`、`faccessat`、`stat`、`lstat`、
`rename`、`unlink`、`mkdir`、`opendir`。

路径映射规则：

| 原始路径 | 映射到 |
|---|---|
| `/data/data/<vpk>/…` | `<space>/data/<vpk>/…` |
| `/data/user/0/<vpk>/…` | `<space>/user/0/<vpk>/…` |
| `/sdcard/…` | `<space>/sdcard/…` |
| `/storage/emulated/0/…` | `<space>/sdcard/…` |
| `/data/media/0/…` | `<space>/sdcard/…` |

其中 `<vpk>` 是当前进程代理的虚拟包名。**相对路径不做重定向**，交给 `dirfd` 语义处理。
匹配包名时检查后一个字符必须是 `/` 或字符串结束，避免 `com.foo` 误匹配 `com.foobar`。

## 六、降级策略

工程在**没有接入真引擎**时也能完整运行，只是能力受限：

| 能力 | 真引擎 | 降级沙箱 |
|---|---|---|
| 创建 / 删除空间 | ✅ | ✅ |
| 空间目录与元数据落盘 | ✅ | ✅ |
| 装入 APK（拷贝 + 解析 manifest） | ✅ | ✅ |
| 运行未安装的 APK | ✅ | ❌ |
| 同应用多开 | ✅ | ❌ |
| 容器级签名伪造 | ✅ | ❌ |
| 谷歌环境装配编排 | ✅ | ⛔ 前置校验直接拦截 |

这个设计让 UI、编排逻辑、文件布局都能在 CI 和无 NDK 环境下验证，
也让"哪一步缺能力"这件事在自检面板上一目了然。
