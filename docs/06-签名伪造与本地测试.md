# 签名伪造：临时证书、跳过，与本地测试

> 一句话结论：
> **本地测试不需要签名伪造，直接跳过即可**（默认就是关闭的）。
> **临时证书可以用，但它换不来 microG 的认可**——它的价值是验证容器 hook 链路。
>
> 想要真证书？见 [四、路线 C](#路线-c真正让-microg-认可)：
> 用 `tools/extract-gms-cert.sh <你自己设备上的 gms.apk>` 一键导出并自动核对指纹。
> 证书**不随项目分发**，只能自备。

---

## 一、先把话说清楚：为什么"临时证书"骗不过 microG

microG 的签名校验逻辑是**对证书的原始 DER 字节做 SHA-1，再与硬编码常量比对**：

```java
// microG: RomSpoofSignatureChecks / PackageUtils
byte[] digest = sha1bytes(sig.toByteArray());
GMS_PACKAGE_SIGNATURE_SHA1.equals(bytesToSumString(digest));
// GMS_PACKAGE_SIGNATURE_SHA1 = "38918a453d07199354f8b19af05ec6562ced5788"
```

`Signature.toByteArray()` 返回的就是证书的原始 DER 字节。所以：

- 要让校验通过，容器返回的必须是**真实的 Google 平台证书 DER**；
- SHA-1 是单向的，**无法从哈希反推出证书**；
- 因此**任何自签证书都不可能通过**——不是"难"，是数学上不行。

顺带澄清一个流传很广的错误说法：`new Signature(String)` 只是把字符串按 ASCII
取字节，并不能"把 SHA-1 字符串变成证书"。网上"填个 SHA-1 就能伪造"的教程是错的。

### 那临时证书到底有什么用

因为「**伪造没生效**」和「**伪造生效了但证书不对**」是两个完全不同的问题：

| 现象 | 说明什么 | 怎么修 |
|---|---|---|
| 容器返回的仍是 microG 自己的签名 | hook 链路**没通** | 检查 AAR 是否打过补丁、钩子是否注册 |
| 容器返回的确实是我配置的证书，但不是 Google 的 | 链路**通了** | 换成真证书即可 |

临时证书能把这两种情况区分开。这就是它的全部价值。

## 二、本地测试到底需不需要它？——不需要

microG 栈的主链路**不依赖签名伪造**：

| 功能 | 依赖签名伪造？ | 说明 |
|---|---|---|
| 登录 Google 账号 | ❌ | microG 走自己的 OAuth 流程，与本地签名无关 |
| 下载安装应用（Aurora Store） | ❌ | Aurora Store 官方兼容 microG，不校验 GMS 签名 |
| 应用多开 / 数据隔离 | ❌ | 纯虚拟化能力 |
| GCM 推送 / 定位 | ❌ | 由 microG 自己提供 |
| **第三方应用检查"Google Play 服务是否可用"** | ✅ | 这类应用会读 GMS 签名，不匹配就报错 |

也就是说：**跳过签名伪造，本地能验证的功能是 95%**。

所以默认值是 `OFF`。这不是"降级"，是**刻意的默认**——把默认值设成需要自备证书
才能工作的状态，只会让每个新用户一上来就看到满屏红字。

## 三、三种模式

空间详情 → 「签名伪造」区块：

| 模式 | 证书来源 | 能骗过 microG | 用途 |
|---|---|---|---|
| **关闭**（默认） | — | — | 本地测试。容器行为与未启用伪造时完全一致 |
| **本地测试证书** | `tools/gen-test-cert.sh` 生成 | ❌ | 验证 hook 链路是否打通 |
| **Google 官方证书** | 使用者自备 | ✅ | 唯一能让 microG 认可的模式 |

切换模式只写一个 JSON 文件，不需要重启应用。容器侧的钩子有 3 秒 TTL 缓存，
改完最多 3 秒生效。

## 四、本地测试：完整流程

### 路线 A：跳过签名伪造（推荐，3 分钟）

1. 新建空间
2. 空间详情 → 「装配谷歌环境」→ 等 microG 装完
3. **「签名伪造」保持「关闭」**（默认就是）
4. 「应用商店」→ 「装入应用商店」（Aurora Store）
5. 「谷歌账号」→ 「登录 Google 账号」
6. 打开空间里的 Aurora Store，搜索并下载应用——下载的 APK 会自动装进这个空间
7. 跑一次自检确认

自检里「签名伪造」组会显示 `SKIP`（不是 FAIL），并说明它不影响主链路。

### 路线 B：验证伪造链路（想确认容器 hook 真的生效）

```bash
# 1. 生成一张自签测试证书
tools/gen-test-cert.sh

# 2. 推到设备（debug 包不需要 root）
adb push local/signature/test_platform.der \
    /sdcard/Android/data/com.dooble.space.debug/files/dooble/signature/

# 3. 应用内：空间详情 → 签名伪造 → 选「本地测试证书」
# 4. 空间详情 → 自检
```

自检里应该看到：

- `证书指纹` → **WARN**，说明"不是官方证书"（符合预期）
- `伪造链路 · com.google.android.gms` → **PASS**，说明容器返回的签名确实被替换了

如果链路那一项是 **FAIL**，说明 `engine/libs/bcore.aar` 是从**未打补丁**的上游源码编的，
按下面的「六、补丁」重新构建即可。

### 路线 C：真正让 microG 认可

需要真实的 Google 平台证书。**证书不随项目分发**（与"不打包原版 GMS"是同一条
合规红线），只能从你自己合法持有的 GMS APK 里导出。

#### 第一步：拿到 GMS 的 APK

从你手上的真机 / 模拟器上拉，来源最明确：

```bash
adb shell pm path com.google.android.gms
# 输出形如：package:/data/app/~~AbCd==/com.google.android.gms-XyZ==/base.apk
adb pull /data/app/~~AbCd==/com.google.android.gms-XyZ==/base.apk gms.apk
```

（也可以用手上已有的系统镜像里提取的 GMS APK。）

#### 第二步：导出证书

```bash
tools/extract-gms-cert.sh gms.apk
```

脚本会输出证书主体、有效期、SHA-1/SHA-256，并**自动核对** SHA-1 是否等于
`38918a453d07199354f8b19af05ec6562ced5788`：

- 一致 → 打印 ✅，退出码 0，产物写到 `local/signature/google_platform.der`
- 不一致 → 打印 ⚠️，退出码 1，并列出常见原因（拿成了 microG 的包 / 第三方改包）

主体应当是 `CN=Android, OU=Android, O=Google Inc., L=Mountain View, ST=California, C=US`。

#### 为什么不用 `unzip -p ... META-INF/CERT.RSA`

这条老配方**对现代 GMS 包已经失效**：

| 做法 | 能读的签名 | 对现代 GMS 包 |
|---|---|---|
| `keytool -printcert -jarfile` | 只有 v1（JAR） | ❌ 报 "Not a signed jar file" |
| `unzip -p ... META-INF/CERT.RSA` | 只有 v1 | ❌ 解出来是空的 |
| `apksigner verify --print-certs` | v1/v2/v3 | ⚠️ 只有指纹，**拿不到证书字节** |
| `tools/extract-apk-cert.sh` | v1 + v2 + v3/v3.1 | ✅ |

2020 年之后发布的 APK 普遍是 v2/v3 签名，很多**根本没有** v1 签名 ——
Google 的 GMS 包正是这一类。而容器侧需要的是**证书字节本身**
（`new Signature(byte[])`），光有指纹没用。

所以 `tools/extract-apk-cert.py` 直接按规范解析 APK Signing Block：

```
signers[0] → signer → signedData → (digests, certificates) → certificates[0] → 证书 DER
```

每一层都是 length-prefixed 序列，路径是固定的。优先取 v3（其次 v2），
只有在签名块整个缺失时才回退到 v1 的 `openssl pkcs7` 路径。

> 验证方式：对同一个 APK 分别跑两条路径，得到的 DER 应当**逐字节相同**。
> 实测本项目 debug 包（v2/v3-only）与合成 v1 包（同源证书）结果一致。

#### 第三步：投放并启用

```bash
adb push local/signature/google_platform.der \
    /sdcard/Android/data/com.dooble.space.debug/files/dooble/signature/
```

然后在应用里选「Google 官方证书」。自检里 `证书指纹` 会变成 **PASS**。

> `local/` 已在 `.gitignore` 里，不会进版本库。
> 请勿把这张证书提交、分发或打包进 APK。

## 五、证书查找顺序

应用按这个顺序找证书，命中即止：

1. `<filesDir>/dooble/signature/<文件名>` — 内部私有目录
2. `<externalFilesDir>/dooble/signature/<文件名>` — 外部私有目录
   （`/sdcard/Android/data/<包名>/files/...`）。**本地测试主要走这条**，
   `adb push` 即可投递，不需要 root，也不用重新打包 APK
3. `assets/signature/<文件名>` — 随包分发

文件名：测试证书 `test_platform.der`，官方证书 `google_platform.der`。

## 六、容器 hook 是怎么实现的

### 关键位置

Bcore 里 `PackageInfo` 的 `signatures` / `signingInfo` 只有**一个**填充处：

```java
// Bcore: core/system/pm/PackageManagerCompat.java  generatePackageInfo()
if ((flags & PackageManager.GET_SIGNATURES) != 0) {
    if (base == null) pi.signatures = p.mSignatures;   // 容器内 APK 的真实签名
    else              pi.signatures = base.signatures; // 宿主同名包的签名
}
if (BuildCompat.isPie() && (flags & PackageManager.GET_SIGNING_CERTIFICATES) != 0) {
    ...  // Android 9+ 的等价路径
}
```

而 `PackageManagerCompat` 跑在**容器服务进程**（Bcore 的 `:black`），
由 `BPackageManagerService.getPackageInfo/getInstalledPackages` 调用。

### 补丁做了什么

只加了一个**接入点**，没有写死任何策略：

```java
// 新增：core/system/pm/PackageSignatureSpoofer.java
public interface Hook {
    Signature[] spoof(String packageName, int userId);
}
public static Signature[] spoof(String packageName, int userId) { ... }
```

```java
// PackageManagerCompat.generatePackageInfo() 里加三行
Signature[] spoofed = PackageSignatureSpoofer.spoof(p.packageName, userId);
// 然后两条分支都优先用 spoofed
```

**宿主不注入钩子时 `spoofed` 恒为 null，容器行为与未打补丁时逐字节一致。**
所以这个补丁本身是零风险的——这也是把它做成"接入点"而不是"写死策略"的原因：
引擎的职责是让未安装的 APK 跑起来，不是当一款签名伪造工具。

### 宿主侧的实现

`engine/src/bcore/.../BcoreSignatureSpoofer.kt` 实现 `Hook`，由
`BcoreEngine.initialize()` 在**每个进程**注册（尤其是服务进程 `:black`，
签名查询真正发生在那里）。

它按 `userId → spaceId → 策略文件` 查表，带 3 秒 TTL 缓存：

```
<filesDir>/dooble/spaces.json                          → userId ↔ spaceId
<filesDir>/dooble/virtual/<spaceId>/data/.dooble/
        spoof_policy.json                              → 包名 → 证书 DER
```

为什么用文件而不是共享内存：写入方在主进程，读取方在服务进程，为一个几 KB 的
配置搭 Binder 服务或 ContentProvider 的复杂度远高于收益。

### 策略文件格式（跨模块契约）

```json
{
  "mode": "TEST",
  "enabled": true,
  "version": 4,
  "targets": [
    { "packageName": "com.google.android.gms", "sha1": "...", "derBase64": "MIIF..." }
  ]
}
```

写入方在 `gms`（`GmsSignatureSpoof.apply`），读取方在引擎
（`SpoofPolicyCodec`）。两端只有字段名这一个约定，所以：
- 解析器被抽成**零 Android 依赖的纯函数**，放在引擎的主源集；
- `gms` 的单元测试拿**真实序列化输出**直接喂给它做契约验证
  （`SpoofPolicyContractTest`），任何一端改字段名立刻红。

## 七、重新构建带补丁的 AAR

补丁在 `tools/bcore-patch/`，`tools/build-bcore.sh` 会**幂等**地自动应用：

```bash
tools/build-bcore.sh
```

三种情况都能正确处理：没打过就 apply、已打过就 skip、上游改了相关代码就报错退出
（而不是留下一个半成品 AAR）。

## 八、常见问题

**Q：自检里「签名伪造」是 SKIP/WARN，是不是环境坏了？**

不是。`SKIP` 表示明确关闭，`WARN` 表示证书不是官方的。两者都**不影响**
账号登录、应用下载、多开。只有 `伪造链路` 那一项 FAIL 才说明引擎侧有问题。

**Q：我用了测试证书，为什么 microG 还是说签名不对？**

因为它确实不对——这是预期行为。测试证书只能验证链路，见第一节。

**Q：能不能干脆改 microG 让它接受我的证书？**

理论上可以（microG 是 Apache-2.0），但需要完整的 Android 构建环境来重编
GmsCore，成本极高。而且这么做的收益只是"让自检变绿"，功能上没有任何提升。
本工程不做这件事。

**Q：为什么不做成默认开启？**

因为默认开启就需要每个使用者自备 Google 证书，否则一进来就是红字。
默认关闭、按需开启，对"先跑起来看看"的本地测试体验最好。

**Q：容器 hook 会不会影响其他应用？**

不会。策略里只列了 4 个包（`com.google.android.gms` / `com.google.android.gsf` /
`com.android.vending` / `com.google.android.maps`），其余包走容器原有逻辑。
