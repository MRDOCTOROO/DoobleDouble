# 本地测试与模拟器适配

本文记录在 **x86_64 模拟器（MuMu）** 上实测 Dooble Double 的全过程与结论。
里面有两个**必修的坑**——它们不是模拟器特有的，不修的话在**真机上同样会失败**，
而且失败方式非常隐蔽（引擎静默降级，UI 看起来完全正常）。

---

## 一、结论先行

| 能力 | MuMu 上能否验证 |
|---|---|
| 安装 / 启动 / UI 渲染 | ✅ 完全正常 |
| 虚拟化引擎加载（真 Bcore，非降级沙箱） | ✅ 正常 |
| 容器服务进程 `:black` 启动 | ✅ 正常 |
| 引擎能力如实上报（设置页） | ✅ 正常 |
| 创建空间 / 装配谷歌环境 / 多开 | ✅ 正常（adb 可驱动，见 5.3） |
| 容器内应用启动（Aurora Store 实测跑通） | ✅ 正常 |
| JNI Hook（隐藏 API 绕过等） | ❌ 翻译层下不可用（见第六节） |

> **一条实测跑通的完整链路**（全部用 adb 驱动）：
> 启动应用 → tap 空间卡片 → tap 桌面图标 → 容器内 Aurora Store 正常启动。

## 二、坑一：`:black-reflection` 缺失（必修，真机同样中招）

### 症状

App 能装、能启动、UI 完全正常，但引擎初始化失败：

```
NoClassDefFoundError: Failed resolution of:
  Ltop/niunaijun/blackreflection/BlackReflection;
  at top.niunaijun.blackbox.BlackBoxCore.<init>() (BlackBoxCore.java:117)
  at com.dooble.engine.bcore.BcoreEngine.getCore() (BcoreEngine.kt:85)
  at com.dooble.engine.bcore.BcoreEngine.bootstrapHost (BcoreEngine.kt:94)
  at com.dooble.space.DoobleApp.attachBaseContext (DoobleApp.kt:15)
```

因为发生在 `attachBaseContext` 里，表现是「引擎静默降级到 SandboxEngine」——
UI 照常显示，只是"多开"功能实际不可用。**极易被误判成"模拟器架构不支持"。**

### 根因

Bcore 的 `build.gradle`：

```groovy
implementation(project(":black-reflection"))
```

`:black-reflection` 是上游源码树里的**独立 `java-library` 模块**（纯 JDK 反射框架，
19 个源文件，零外部依赖）。两个后果叠加：

1. `implementation` 而非 `api` → **AAR 不传递**，`classes.jar` 里根本没有
   `blackreflection` 包；
2. 它是**本地源码模块，没有 Maven 坐标** → 不能像 FreeReflection 那样用
   `libs.xxx` 声明，Gradle 也捞不回来。

这和「本地 AAR 不带传递依赖」是同一类问题，但前面只补了 Maven 侧的
（FreeReflection、ConstraintLayout），漏了本地模块这一种。

### 修法

`tools/build-bcore.sh` 里增加一步，把 `:black-reflection` 单独编成 jar：

```bash
./gradlew.bat :black-reflection:jar --no-daemon
# 产物 black-reflection/build/libs/black-reflection.jar → engine/libs/
```

`:app` 的 fileTree 同时收 `*.jar`：

```kotlin
implementation(fileTree("../engine/libs") { include("*.aar", "*.jar") })
```

### 怎么系统性排查同类问题

不要靠运行时一个个撞。用 `jdeps` 静态扫一遍：

```bash
# 1. 从 AAR 里取出 classes.jar
# 2. 列出所有引用
jdeps -verbose:class classes.jar > jdeps.txt

# 3. 找出「被引用但不在 jar 内」的类
#    第 3 列是目标类名；与 jar 内实际类名做差集
```

修复后应该只剩这几类**正常的**"缺失"：

| 缺失的类 | 为什么正常 |
|---|---|
| `top.niunaijun.blackbox.R` / `R$id` / `R$layout` | AAR 只带 `R.txt`，`R` 类由**消费方 AGP 生成** |
| `androidx.core.*` | 已在 `app` 显式声明 `androidx.core.ktx` |
| `me.weishu.reflection.Reflection` | 已显式声明 FreeReflection |

## 三、坑二：混合 ABI 让 `libblackbox.so` 永远找不到（必修）

### 症状

```
UnsatisfiedLinkError: dlopen failed: library "libblackbox.so" not found
  at top.niunaijun.blackbox.core.NativeCore.<clinit>() (NativeCore.java:26)
  at BlackBoxCore.setEssentialProperties (BlackBoxCore.java:1647)
  at BcoreEngine.bootstrapHost (BcoreEngine.kt:96)
```

日志里的 `library_path` 说明了一切：

```
library_path=.../lib/x86_64:.../base.apk!/lib/x86_64
```

**只有 `lib/x86_64`**，而 Bcore 上游只提供 `arm64-v8a` / `armeabi-v7a` 的
`libblackbox.so`。

### 根因：Android 的 primaryCpuAbi 是「每个 APK 一个」

安装时系统按 `ro.product.cpu.abilist` 的顺序，挑**第一个在 APK 里存在**
的 ABI 作为 `primaryCpuAbi`，之后 `nativeLibraryDir` 就**固定**成
`lib/<该 ABI>`，**不会**为单个 `.so` 回退到别的目录。

所以只要 APK 里出现 `lib/x86_64/`，哪怕里面只躺着一个第三方库
（比如 Compose 传递依赖带进来的 `libandroidx.graphics.path.so`），
`primaryCpuAbi` 就会是 `x86_64`，`System.loadLibrary("blackbox")` 必然失败。

**这是最容易踩的地方**：`:native` 模块自己编 x86_64 是合理的（想在模拟器上调试
native 代码），但它会顺带把整个 App 的 ABI 选择带偏。

### 修法

用 `defaultConfig.ndk.abiFilters` —— 它会过滤**合并后**的全部 native 库，
包括第三方传递进来的：

```kotlin
// app/build.gradle.kts
defaultConfig {
    ndk {
        abiFilters += listOf("arm64-v8a", "armeabi-v7a")   // 绝不放 x86_64 / x86
    }
}
```

`:native` 模块的 `abiFilters` 要同步改，否则白编一遍。

将来若 Bcore 提供 x86_64 的 `libblackbox.so`，把两处一起加回 `"x86_64"`。

## 四、MuMu 的环境事实

实测（MuMu 12，Android 15 / API 35）：

```
ro.product.cpu.abi              = x86_64
ro.product.cpu.abilist          = x86_64,arm64-v8a,x86      ← 含 arm64-v8a
ro.build.version.release        = 15
ro.build.version.sdk            = 35
ro.dalvik.vm.native.bridge      = libnb.so                  ← 自研 ARM 翻译层
```

启动 App 时 native bridge 会以 arm64 模式初始化：

```
V/libnb: enter native_bridge2_initialize /data/user/0/.../code_cache arm64
W/HP   : x_initialize private_dir:... instruction_set:arm64
```

所以 **去掉 `x86_64` / `x86` 后，`primaryCpuAbi` 落到 `arm64-v8a`，
`lib/arm64-v8a/` 里三个 `.so` 齐全，`libblackbox.so` 在翻译层下能正常加载**：

```
D/NativeCore: NativeCore init.
D/BlackBoxCore: NativeCore initialized successfully
D/BlackBoxCore: getService: package_manager, BPackageManagerService@...
D/BlackBoxCore: Services initialized successfully
D/BlackBoxCore: BlackBox initialization completed in 823ms
```

验证 `primaryCpuAbi` 是否修好：

```bash
adb shell dumpsys package com.dooble.space.debug | grep primaryCpuAbi
# 期望 primaryCpuAbi=arm64-v8a
```

## 五、用 adb 操作 MuMu 的注意事项

这几点都踩过，写下来省时间。

### 5.1 adb server 在两次 shell 调用之间会被回收

表现：每条命令都报 `daemon not running; starting now` 然后 `device not found`。

**所以「连接 → 安装 → 启动 → 抓日志」必须在同一次进程里完成。**
用 `tools/run-on-mumu.sh`，它会把整套流程串起来。

手敲命令时，**每次 Bash 调用都要以这两句开头**：

```bash
ADB="C:/Users/admin/android-dev/sdk/platform-tools/adb.exe"   # adb 不在 PATH 里
"$ADB" connect 127.0.0.1:16384
```

并且每条命令都带 `-s 127.0.0.1:16384`——设备列表里同时存在
`127.0.0.1:16384` 与 `emulator-5554`，不带 `-s` 会报
`more than one device/emulator`。

### 5.2 MuMu 的 adb 端口不固定

| 端口 | 说明 |
|---|---|
| `16384` | MuMu 12 |
| `7555` | 老版本 MuMu |
| `5555` | 标准 AVD |

三个端口可能同时开放且指向**同一台设备**（product 都伪装成 `V2245A`）。
脚本会自动探测并挑 x86_64 那台。

### 5.3 触摸注入没问题，坑在坐标系

> ⚠️ **本节修正了早先的一个错误结论。** 之前这里写的是
> 「MuMu 走自己的输入管线，adb 注入的触摸事件会被丢掉」——**那是错的**。
> 实测 `input tap` / `input swipe` 都完全正常，当时的失败纯粹是**坐标算错了**。

| 事实 | 值 |
|---|---|
| `wm size` 报的 `Physical size` | `1440x2560`（面板**自然方向**，竖屏） |
| 实际逻辑分辨率（MuMu 当前横屏） | `2560x1440` |
| `screencap` 出来的 PNG | `2560x1440` |

`input tap x y` 用的是**逻辑分辨率**。拿 `wm size` 的 `1440x2560` 去算坐标，
点出来的位置和预期完全对不上，看起来就像"事件被丢掉了"。

**正确做法：以截图 PNG 的像素尺寸为准。** 在 PNG 上量到多少就是多少，
不要拿任何被缩放过的预览图去量——那正是当初算错的来源。

```bash
adb shell screencap -p /sdcard/s.png
adb pull /sdcard/s.png
python3 -c "import struct;d=open('s.png','rb').read(33);print(struct.unpack('>II',d[16:24]))"
# (2560, 1440)  ← 用它，不要用 wm size
```

实测：空间卡片中心在 PNG 上是 `(1282, 612)`，`input tap 1282 612` 精确命中。

`input swipe` 同样可用，用来滚动页面：

```bash
adb shell input swipe 1280 400 1280 1300 300   # 向下滑回顶部
```

**结论：可以用 adb 自动跑 UI 流程。** 下面这条链路已实测跑通：

```
启动应用 → tap 空间卡片 → tap 桌面图标 → 容器内 Aurora Store 启动成功
```

DPAD 也能用，适合"按顺序遍历控件"：

```bash
adb shell input keyevent KEYCODE_DPAD_DOWN
adb shell input keyevent KEYCODE_DPAD_CENTER   # 激活当前焦点
```

但焦点顺序按布局走，第一次 `KEYCODE_DPAD_DOWN` 未必落在你预期的控件上
（实测直接跳到了「新建空间」按钮，而不是上面的空间卡片）。
要精确定位还是 tap + 截图更可靠。

> 附带一个判断陷阱：本工程是**单 Activity + Compose 内部路由**，
> 所以进入设置页后 `ResumedActivity` **仍然是 `MainActivity`**。
> 想用 `dumpsys activity activities | grep ResumedActivity` 判断"有没有跳转"
> 是判断不出来的，必须截图。
>
> 例外：容器内应用启动时 `topResumedActivity` 会变成
> `top.niunaijun.blackbox.proxy.ProxyActivity$P0`，
> 所以**判断"虚拟应用有没有起来"用这一条是可靠的**。

### 5.4 屏幕是横屏，`wm size` 会骗人

MuMu 的显示会随窗口在横屏 / 竖屏之间切换。`dumpsys window displays` 里的
`cur=` 才是当前逻辑分辨率，截图尺寸与它一致。

**一律以截图 PNG 的尺寸为准算坐标**，不要用 `wm size` 的 `Physical size`
（那是自然方向），也不要用 `dumpsys window` 里其它看起来像分辨率的字段。

### 5.5 点击坐标一律用 `uiautomator dump` 算，不要目测

本工程是 Compose UI，截图在对话里会被缩放渲染，**目测坐标必偏**（本轮连点错过两次：
一次点到了相邻的行，一次因为屏幕被启动器转成横屏，按竖屏算的坐标全错位）。

正确做法：

```bash
adb shell uiautomator dump /sdcard/u.xml
adb pull /sdcard/u.xml
# 解析 bounds="[x1,y1][x2,y2]" 取中心点 (x1+x2)/2, (y1+y2)/2
```

两个 Compose 特有的坑：

1. **文本节点本身不可点击**，可点击的是它的祖先容器。
   拿到目标文本的 bounds 后，要向上找第一个 `clickable="true"` 的祖先，
   用那个祖先的中心点。
2. **图标按钮没有 text，只有 `content-desc`**。比如「结束运行」「启动」「卸载」
   三个按钮都是纯图标，只能靠 `content-desc` 区分。

再顺手把方向锁死，避免启动器改屏幕方向：

```bash
adb shell settings put system user_rotation 0
adb shell settings put system accelerometer_rotation 0
```

### 5.6 容器里的虚拟进程在 `/proc` 里是「伪装名」

**这一条会让人误判"虚拟应用没起来"。**

`ps -A | grep com.dooble.space` 只会看到宿主自己的两个进程：

```
u0_a51  16931  com.dooble.space.debug          ← 宿主主进程
u0_a51  17040  com.dooble.space.debug:black    ← Bcore 的 DaemonService
```

容器内运行的虚拟应用**看不到**——因为它们做了进程伪装，`/proc/<pid>/cmdline`
是**被冒充的那个应用自己的包名**：

```
17406  com.google.android.gms:ui      ← 容器内的 microG 服务
18189  com.aurora.store               ← 容器内的 Aurora Store
```

所以判断"某个容器内应用还在不在"，要按被冒充的包名去找：

```bash
adb shell 'for p in $(ls /proc | grep -E "^[0-9]+$"); do \
  c=$(tr "\0" " " < /proc/$p/cmdline 2>/dev/null); \
  case "$c" in *aurora*|*google.android.gms*|*vending*) echo "$p $c";; esac; done'
```

另外 `dumpsys activity processes` 里能看到容器侧的进程记录
（`ProcessRecord{... <pid>:com.dooble.space.debug:pN/u0a51}`，
`Activities: ... ProxyActivity$PN`），可以作为交叉验证。

## 六、已知限制：JNI Hook 在 ARM 翻译层下不可用

```
E/NativeCore: init jni hook error. art_method_native_offset not found!
```

这条是 **non-fatal**（只打日志，Bcore 继续初始化），但意味着 JNI Hook 未启用。

原因在 `Bcore/src/main/cpp/JniHook/JniHook.cpp:243-255`：它靠**扫描 `ArtMethod`
结构体里的指针值**，找到与 `nativeOffset()` 的 JNI 函数指针相等的那个槽位，
从而定位 `art_method_native_offset`：

```cpp
for (i = 0; i < HookEnv.art_method_size; ++i) {
    if (reinterpret_cast<void *>(artMethod[i]) == native_offset) { ... }
}
```

在 ARM 翻译层下，`ArtMethod` 里存的是**翻译后**的地址，与通过
`GetArtMethod` 拿到的函数指针不是同一个值，比对必然失败。

**判断**：这大概率是翻译层的产物，而不是 Android 15 本身的问题。
真机（arm64 原生）上是否可用**尚未验证**——需要一台 arm64 真机才能定论。
在那之前，不要假设 `disableHiddenApi` / `hideXposed` / `getCallingUid` hook 生效。

## 七、怎么跑

```bash
export ANDROID_HOME="C:/Users/admin/android-dev/sdk"

# 构建 + 拷到 dist/
./gradlew.bat :app:assembleLiteDebug --no-daemon
cp app/build/outputs/apk/lite/debug/app-lite-debug.apk dist/dooble-lite-debug.apk

# 一键：连接 → 安装 → 启动 → 抓日志
tools/run-on-mumu.sh
tools/run-on-mumu.sh abi      # 只看架构与 primaryCpuAbi
tools/run-on-mumu.sh logcat   # 持续看引擎日志
```

跑完确认三件事：

1. `primaryCpuAbi=arm64-v8a`
2. 日志里有 `NativeCore initialized successfully`
3. `ps -A | grep dooble` 能看到**两个**进程：
   `com.dooble.space.debug` 和 `com.dooble.space.debug:black`
