# 10 · 谷歌账号登录链路（含一次实测排查）

本文记录「点『登录 Google 账号』只弹出一个点不动的『添加账号』页面」这个 bug 的
完整排查与修复，以及修好之后在模拟器上撞到的下一个问题。

**结论先行**：登录入口必须在**容器内**解析和启动。宿主 PackageManager 看不到
空间里的包，任何用宿主 PMS 做的判断都是错的。

---

## 1. 现象

用户报告：

> 点击登录谷歌账号页面可以唤起页面，但只有「添加账号」字符，无法下一步操作。

宿主机的 tun 网卡已正常穿透到 MuMu 模拟器，模拟器内可以正常访问谷歌 ——
所以**不是网络问题**。

---

## 2. 根因：三条错误同时成立

出问题的是 `GoogleAccountBridge.signInIntent()`，原来的实现是：

```kotlin
fun signInIntent(spaceId: String): Intent {
    val microGLogin = Intent("org.microg.gms.auth.LOGIN").apply { ... }
    if (context.packageManager.resolveActivity(microGLogin, 0) != null) return microGLogin  // ① 宿主 PMS
    return Intent(Settings.ACTION_ADD_ACCOUNT_SETTINGS)                                       // ③ 兜底
}                                                                                             // ② action 是编的
```

| # | 问题 | 事实 |
|---|---|---|
| ① | 用**宿主** `PackageManager.resolveActivity()` 解析 | 空间里的包对宿主 PMS **不可见**，永远返回 `null` |
| ② | action 字符串 `org.microg.gms.auth.LOGIN` 是**编的** | microG 清单里没有这一条 |
| ③ | 兜底是 `ACTION_ADD_ACCOUNT_SETTINGS` | 打开的是**宿主**的账号设置页，那里没有 microG 的 authenticator |

三条串起来的表现就完全对上了：宿主查不到 → 走兜底 → 打开宿主的系统账号页 →
那页上唯一能显示的就是一个「添加账号」入口，而它下面没有任何 provider，
**所以点不动**。

不是查文档、不是猜，是从 APK 清单里读出来的：

## 3. 修复：给引擎加"容器内解析 / 启动"能力

### 3.1 引擎接口新增两个方法

```kotlin
/** 在空间内解析一个 intent，返回容器里真正能处理它的组件 */
suspend fun resolveActivityInSpace(spaceId: String, intent: Intent): ComponentName? = null

/** 在空间内启动一个 intent */
suspend fun launchIntent(spaceId: String, intent: Intent): LaunchResult =
    LaunchResult.fail("当前引擎不支持在空间内启动指定 intent")
```

`BcoreEngine` 的实现走容器自己的 PMS / AMS：

```kotlin
override suspend fun resolveActivityInSpace(spaceId: String, intent: Intent): ComponentName? {
    val userId = userIdOf(spaceId)
    if (userId <= 0) return null
    val info = BPackageManager.get().resolveActivity(intent, 0, null, userId)  // ← 容器 PMS
    return info?.activityInfo?.let { ComponentName(it.packageName, it.name) }
}

override suspend fun launchIntent(spaceId: String, intent: Intent): LaunchResult {
    // 容器必须自己解析一遍：宿主进程直接 startActivity 会把 intent 交给 system_server，
    // 而 intent 里写的包名在宿主上是不存在的（它是空间内的虚拟包）
    val resolved = resolveActivityInSpace(spaceId, intent)
        ?: return LaunchResult.fail("空间内没有组件能处理该请求")
    val explicit = Intent(intent).apply {
        component = resolved
        addFlags(Intent.FLAG_ACTIVITY_NEW_TASK)
    }
    return if (runCatching { core.startActivity(explicit, userId) }.isSuccess) {
        LaunchResult.ok()
    } else LaunchResult.fail("启动失败：$resolved")
}
```

### 3.2 登录入口按优先级尝试三个候选

```kotlin
val attempts = listOf(
    "登录界面（显式组件）" to Intent().setComponent(ComponentName(GMS_PACKAGE, LOGIN_ACTIVITY)),
    "登录界面（action）" to Intent(ACTION_MICROG_LOGIN).setPackage(GMS_PACKAGE),
    "账号选择器"       to Intent(ACTION_CHOOSE_ACCOUNT).setPackage(GMS_PACKAGE),
)
for ((label, intent) in attempts) {
    val resolved = engine.resolveActivityInSpace(spaceId, intent)
    Log.i(TAG, "[$spaceId] $label 解析结果=$resolved")   // ← 每步都记日志
    if (resolved == null) { lastReason = "$label 未在空间内注册"; continue }
    val result = engine.launchIntent(spaceId, intent)
    Log.i(TAG, "[$spaceId] $label 启动结果 ok=${result.ok}")
    if (result.ok) return result
}
```

三个都解析不到，就**如实返回失败**并提示"请先装配 microG"——
**绝不再回退到宿主系统设置页**，那只会给用户一个点不动的空页面。

> **可观测性**：这条链路失败原本是**完全静默**的（只弹个 toast）。
> 每步都打日志之后，"点了没反应"就能区分出是"容器没解析到"还是
> "解析到了但启动失败"。这类跨进程链路一定要在关键分支留日志。

### 4.2 撞到的下一个问题：WebView 画面空白（模拟器 GPU 限制）

URL 加载完成，但 WebView 区域是白的，microG 的「请稍等…」遮罩一直不消失。
Chromium 日志给出了原因：

```
E chromium: [ERROR:tile_manager.cc(826)] WARNING: tile memory limits exceeded,
            some content may not draw
```

**这是模拟器的 GPU tile 内存预算不够，不是本工程的 bug。**
MuMu 是 x86_64 + ARM 翻译层 + 受限显存，而 WebView 是全屏硬件加速渲染，
预算打满之后 Chromium 就不画了。

试过的绕过办法（都没成功，记录下来免得重复试）：

| 尝试 | 结果 |
|---|---|
| `/data/local/tmp/webview-command-line` 写 `--disable-gpu --use-gl=swiftshader` | ❌ 无效（该文件只在 debuggable 应用 / userdebug 构建上生效） |
| `wm size 1280x720` + `wm density 240` 降低渲染面积 | ❌ 仍然 tile 超限 |
| `--disable-features=DefaultEnableGpuRasterization` | ❌ 无效 |

**建议**：在**真机**上验证 WebView 渲染。模拟器上做到"能拉起登录界面、
能加载 Google 页面"已经足够验证容器侧链路是通的。

> 顺便记一个反例：`adb shell cat` 导出 APK 在 Windows 上会因换行转换破坏 zip。
> 必须用 `adb exec-out ... > file`（不经 PTY，二进制安全）。

## 6. 第二个案例：Aurora Store 点「Google」没反应，随后 ANR

### 6.1 现象

> 应用内的 Aurora Store 点击下一步没反应会卡在那，一会还会卡 Dooble 的应用没有响应。

网络没问题（tun 已穿透）。ANR 的对话框写着「Dooble 没有响应」，
但**真正的 ANR 进程是空间里的 Aurora Store** —— 见 6.4 的解释。

### 6.2 根因：账号选择器跑在**宿主进程**里

Aurora 的「Google」按钮调 `AccountManager.newChooseAccountIntent()`。
这个 API 返回的是一条**显式指向宿主系统包**的 intent：

```
ComponentName("android", "android.accounts.ChooseTypeAndAccountActivity")
```

容器能解析它（宿主系统包在容器里可见），于是 Bcore 把它**转发给真实系统**，
它真的在宿主进程 `android:ui`（uid 1000）里跑起来了：

```
16:13:00.608  D CommonStub: Hook in : Intent { cmp=android/.accounts.ChooseTypeAndAccountActivity (has extras) }
16:13:00.619  I ActivityTaskManager: START u0 {cmp=android/.accounts.ChooseTypeAndAccountActivity} ... from uid 10051
16:13:00.634  I ActivityManager: Start proc 45307:android:ui/1000 for next-top-activity   ← 宿主进程！
16:13:00.727  I ActivityTaskManager: START u0 {flg=0x80000 cmp=android/.accounts.ChooseAccountTypeActivity}
16:13:00.836  D AccountChooser: ChooseTypeAndAccountActivity.onActivityResult:
                                  unable to find account type, pretending the request was canceled
16:13:00.842  → CLOSE 过渡，页面立刻关掉
```

`ChooseTypeAndAccountActivity` 查的是**它自己所在进程**的 AccountManager。
宿主上没有任何 `com.google` 的 authenticator（microG 装在**空间里**），
于是它立刻判定"没有账号类型"，返回 `RESULT_CANCELED` 并关闭。

Aurora 收到取消 → 页面不动。用户看到的就是「点了没反应」。

> **一句话**：microG 在空间里，账号选择器在宿主里，两边看不到对方。

### 6.3 修法：容器侧把账号选择器改道到 microG 的登录界面

新增 `tools/bcore-patch/0005-account-chooser-redirect.patch`。这一版踩了**两个坑**，
都记在这里，因为它们比结论本身更有用。

#### 坑一：改道点必须在 `resolveInfo == null` 的兜底分支里

```java
ResolveInfo resolveInfo = ...resolveActivity(intent, ...);
if (resolveInfo == null) {
    ...
    if (resolveInfo == null) { resolveInfo = resolveStoreIntent(intent); }
    if (resolveInfo == null) {
        resolveInfo = resolveAccountChooser(intent);   // ✅ 必须在这里
    }
    if (resolveInfo == null) {
        intent.setPackage(origPackage);
        return method.invoke(who, args);               // ← 原始 intent 被丢给真实系统
    }
}

// ❌ 放在这里（下面的通用路径）永远不会执行：
//    容器根本解析不到，上面就已经 return 了。
//    第一版就写在这里，logcat 里连 probe 日志都没有。
```

**为什么容器解析不到**：宿主系统包（`android`）的活动**不在容器的组件表里**，
`resolveActivity` 返回 null，于是代码走兜底分支，把**原始 intent** 丢给真实系统。
这才是"账号选择器跑在宿主进程"的直接原因。

因此判断依据也必须换成 **intent 自己的 component**，而不是解析结果。

#### 坑二：目标不能用 `AccountPickerActivity`（会无限递归）

第一版把目标设成 `org.microg.tools.AccountPickerActivity`（语义上最接近"选一个账号"）。
结果：

```
17:06:46.002  AppInstrumentation: callActivityOnCreate: org.microg.tools.AccountPickerActivity
17:06:46.007  CommonStub: Hook in : Intent { cmp=android/.accounts.ChooseTypeAndAccountActivity }
17:06:46.008  Redirect account chooser ... -> AccountPickerActivity
17:06:46.018  ActivityStack: onFinishActivity : AccountPickerActivity
17:06:46.040  CommonStub: Hook in : ...（同一个 intent 又来了）
→ 200ms 内循环刷屏
```

**`AccountPickerActivity` 是个包装层** —— 它在 `onCreate` 里自己也调
`AccountManager.newChooseAccountIntent()`，于是被我们改道回它自己。

改法两条：
1. 目标换成真正干活的 `org.microg.gms.auth.login.LoginActivity`（它不会回头调账号选择器）；
2. 加**环路保护**：改道时往 intent 里塞一个标记 extra（`_dooble_account_redirect_`），
   下次进钩子看到标记就直接放行。

#### 三条安全约束

- **只认 `component.packageName = "android"`**。别的包一律不动 —— 猜错会把正常应用自己的账号页面也劫持掉。
- **空间里没有 microG 时保持原样**，并打 `Slog.w`。宁可让用户看到系统那个空页面，
  也不要凭空造一个不存在的组件名。
- 类名按**后缀**匹配（`accounts.ChooseTypeAndAccountActivity` 等三个），避免绑死具体版本。

#### ⚠️ 已知限制：改了这里 Aurora 的 Google 登录**仍然完成不了**

改道让「添加账号」这条路可达了（点「Google」会打开 microG 的登录界面），
但 **Aurora 自己的 Google 登录流程仍然走不完**：

Aurora 读的是 `onActivityResult` 里的 `KEY_ACCOUNT_NAME`，而 `LoginActivity`
不会回填那个结果 —— Aurora 仍然收到 `RESULT_CANCELED`，页面仍然不动。

要真正打通，需要**往空间里装一个我们自己实现的"账号选择器" APK**：
它声明一个能被改道命中的组件，在空间内查询 microG 的账号列表，
选中后 `setResult(RESULT_OK, Intent().putExtra(KEY_ACCOUNT_NAME, name))`。
那样才满足 Aurora 的返回契约。属于后续工作。

**当前可用的替代**：Aurora 的「匿名」会话。Aurora 官方支持，不需要 Google 账号，
一样能搜索和下载应用。UI 上已经把这条写出来了。

### 6.3.1 排查这类问题的一般方法

这次的定位路径值得复用：

1. **先看 logcat 里的"谁在处理"**。`CommonStub: Hook in : Intent {...}` 只说明
   钩子跑了，**不说明容器认领了它**。
2. **再看 `ActivityTaskManager: START ... from uid <谁>`**。`from uid 10051`
   是我们自己的 uid（容器转发），`Start proc ...:android:ui/1000` 说明目标活动
   跑在**宿主系统进程**里 —— 这就是"看不到空间内 microG"的直接证据。
3. **拿不到结论时，加无条件日志再跑一次**。第一版补丁的三条 early-return 都是
   静默的，结果连"没进 probe"都看不出来，白跑了一轮 9 分钟的 AAR 构建。
   **只要是在做"匹配 + 改道"这类逻辑，每条 early-return 都要留痕。**
4. **改道类逻辑一定要想清楚"改道目标会不会再触发同一条规则"** —— 会的话就是死循环。

### 6.4 为什么 ANR 对话框显示的是「Dooble」而不是「Aurora Store」

因为 Bcore 做了**进程伪装**：虚拟进程在 `/proc` 里的名字是 `com.aurora.store`，
但它**属于宿主的 uid/包**。系统弹 ANR 对话框时用 `ProcessRecord` 的
`ApplicationInfo` 取应用名 —— 那是宿主的，于是显示成「Dooble Double 没有响应」。

ANR trace 的标题写得很清楚：

```
Subject: Input dispatching timed out
         (167b904 com.aurora.store/com.aurora.store.ComposeActivity is not responding.
          Waited 25006ms for MotionEvent)
```

**这不是 Dooble 主进程卡了。** 宿主进程（`com.dooble.space.debug`）根本没出现在
ANR 列表里。

### 6.5 ANR 的直接原因：主循环已退出，窗口还活着

从 trace 里 Aurora 进程（pid 44106）的线程状态能看出来：

```
"om.aurora.store" prio=10 (not attached)     ← 线程名缓冲截断，就是 "com.aurora.store"
  | sysTid=44106 nice=-10
  native: #02 ... art::ThreadList::WaitForOtherNonDaemonThreadsToExit
  native: #03 ... art::JII::DestroyJavaVM
  native: #05 ... android::AndroidRuntime::start
```

主线程停在 **`DestroyJavaVM`** —— 也就是说这个虚拟进程的 Java 主循环
**已经退出了**（`main()` 返回，正在等非守护线程结束），但**窗口还在屏幕上**。
输入事件投给一个已经死掉的主循环 → 25 秒后 ANR。

它是"卡住"这个现象的下游后果：用户点「Google」没反应 → 反复点 →
期间虚拟 Activity 被结束掉了，而窗口没跟着收走。

### 6.6 同一次踩到的构建脚本问题

`tools/build-bcore.sh` 原来用**逐个补丁的 `git apply --reverse --check`**
来判断"是否已应用"。这个判据会被**后加的补丁破坏**：只要新补丁的改动落进了
老补丁的上下文窗口（前后各 3 行），老补丁的 reverse-check 就失败，
脚本报 "Patch does not apply cleanly" 退出。

0005 正好落在 0003 在 `ActivityManagerCommonProxy.java` 的改动窗口里，
于是踩了个正着。修法改成**戳记机制**：

```bash
want="$(cat "${patches[@]}" | git hash-object --stdin)"
# 戳记匹配 + 工作区是脏的 → 说明补丁确实已经打进去了 → 整个环节跳过
```

补丁集合一变哈希就变（戳记自动失效）；工作区被 `git checkout .` 清干净时也失效。

> **教训**：只通过 `tools/bcore-patch/*.patch` 改上游源码，
> 不要在 `nbb-src` 里直接编辑 —— 手改会让所有补丁的自检失去意义。
